## 0. 排障前必读：先确认运行形态

LightMDKit 有**三种运行形态**，同一现象在不同形态下根因完全不同（尤其是「改动不生效」「看不到日志」）：

| 形态 | 启动方式 | 前端资源来源 | 日志可见性 |
|------|---------|-------------|-----------|
| **源码模式** | `npm start` / `start.bat` / `start.sh`（内部执行 `node LightMDKit/server.js`，`LightMDKit/start.bat:28`、`LightMDKit/start.sh:20`） | 实时读取 `LightMDKit/public/` | 仅**前台**运行可见 |
| **打包 exe** | 双击 `LightMDKit/dist/lightmdkit.exe` | pkg 打包时内嵌的 `public/**/*` 快照（`LightMDKit/package.json:11-18`） | **完全不可见**（GUI 子系统 + 无控制台） |
| **守护进程** | 上述两种启动方式都会分离出一个后台进程（环境变量 `LIGHTMDKIT_DAEMON=1`） | 同左 | **不可见**（`spawn` 时 `stdio:'ignore'`，`LightMDKit/server.js:266-271`） |

> **排障第一原则**：默认启动方式是"父进程 fork 守护进程后退出"（`LightMDKit/server.js:299-305`），守护进程的 stdout/stderr 被丢弃（`stdio: 'ignore'`），项目**也没有写任何日志文件**。要看到错误输出，只能用前台模式启动：
>
> ```powershell
> # PowerShell（Windows）
> $env:LIGHTMDKIT_DAEMON='1'; node LightMDKit/server.js
> ```
> ```bash
> # Git Bash / macOS / Linux
> LIGHTMDKIT_DAEMON=1 node LightMDKit/server.js
> ```
> 该模式命中 `main()` 里的守护分支，直接执行 `runDaemon()`（`LightMDKit/server.js:275-275`）——不 fork、不自动打开浏览器，所有 `console.log/console.error` 都打在终端上。

## 2. 日志系统

> **重要前提**：本项目**没有日志文件、没有日志框架、没有日志级别配置**。全部输出依赖 `console.*`，且默认启动路径（守护进程 / exe）会把它们丢弃。因此"看日志"= 用前台模式启动 + 浏览器 DevTools。

| 场景 | 位置 | 备注 |
|------|------|------|
| 前台运行 `node LightMDKit/server.js` | 终端 stdout / stderr | **唯一完整的服务端日志通道**（`LightMDKit/server.js:20,74,282,285,301,307`） |
| 默认启动（`npm start` / `start.bat`） | 无 | 父进程打印 `LightMDKit started at ...` 后 `process.exit(0)`（`LightMDKit/server.js:301-304`）；子进程 `stdio:'ignore'`（`LightMDKit/server.js:268`），日志全部丢弃 |

### 3.1 端口 3456 被占用 / 服务起不来 / 重复启动

**现象**
- 终端（前台模式）报 `Port 3456 is already in use.`；或父进程打印 `端口 3456 已被占用，LightMDKit 可能已在运行。`（`LightMDKit/server.js:282, 307`）
- 启动后浏览器打开的页面**不是** LightMDKit（被别人占用时）
- 双击 exe 毫无反应、也没有任何报错（GUI 子系统 + 日志被丢弃）
- 反复启动后打开多个标签页 / 出现多份服务进程

**可能原因**

| # | 原因 | 判断依据 |
|---|------|---------|
| 1 | 已有 LightMDKit 守护进程在运行（**正常行为**） | 端口被占时 `main()` 只打印提示、打开浏览器然后退出，不会重复启动服务（`LightMDKit/server.js:299-310`） |
| 2 | 3456 被**其它程序**占用 | `tasklist /FI "PID eq <PID>"` 显示的不是 `node.exe`/`lightmdkit.exe`；此时程序仍会打开浏览器，用户会误以为"已经跑起来了"（`LightMDKit/server.js:307-309` 未做身份校验） |
| 3 | 守护进程 fork 后启动失败 | 端口在 `isPortInUse()` 检查之后被抢占 → `EADDRINUSE` → `process.exit(1)`（`LightMDKit/server.js:280-288`），且该错误被 `stdio:'ignore'` 丢弃 |
| 4 | 启动竞态：浏览器先于服务就绪 | `spawnDaemon()` 后只 `sleep(2000)` 就 `openBrowser()`（`LightMDKit/server.js:233-233`）；首次运行 40MB 的 pkg exe 解包可能超过 2s → 页面提示"无法访问此网站" |
| 5 | 端口被安全软件/虚拟化层占用或本地监听被策略拦截 | 无监听但浏览器连不上；换端口可验证 |
| 6 | 残留进程未清理 | `stop.bat` 只按镜像名杀进程（`LightMDKit/stop.bat:6-7`）：以源码模式启动的守护进程是 `node.exe`，若与其它 Node 程序混在一起容易漏杀或误杀 |

**排查步骤**
1. 查端口占用：`netstat -ano | findstr :3456`（Unix：`lsof -i:3456`），记下 PID
2. 查 PID 身份：`tasklist /FI "PID eq <PID>"`（或 `wmic process where processid=<PID> get name,commandline`）
3. 确认端口后面是不是 LightMDKit：`curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3456/`（正常返回 `200`），或直接看返回内容
4. **前台启动看真实报错**：`$env:LIGHTMDKIT_DAEMON='1'; node LightMDKit/server.js`
   - 打印 `Port 3456 is already in use.` 并在数秒内退出 → 端口确被占用（回到第 1 步）
   - 不打印任何错误且能访问 → 说明只是上次启动的竞态，刷新浏览器即可
5. 若是 exe 形态：改用源码模式复现（exe 无日志，见第 0 节）

**解决方案**
1. 已在运行：直接访问 <http://localhost:3456>，不要重复启动
2. 确实需要重启：Windows 下 `taskkill /F /IM lightmdkit.exe`，再用精确 PID 结束对应的 `node.exe`（**不要**直接 `taskkill /F /IM node.exe`，会误杀机器上其它 Node 程序）；Unix 用 `pkill -f "node server.js"`（`LightMDKit/stop.sh:6`）
3. 端口长期被别的程序占用：修改 `LightMDKit/server.js:11` 的 `PORT`（硬编码，无配置项、无环境变量覆盖）。改动后注意同步 README 与本文档中的 3456 引用
4. 首次启动/双击 exe 后连不上：手动 F5 刷新浏览器一次；仍失败则按第 4 步前台启动定位
5. **注意文档与实现的差异**：README 中"提示选择「重新运行」或「显示访问 URL」"的交互在当前 `main()` 中**不存在**（`LightMDKit/server.js:291-311` 只打印提示并打开浏览器），排查时不要按交互式提示去预期

**源码位置**：`LightMDKit/server.js:11`（PORT）、`226`、`227`（DAEMON_ENV）、`251-263`（`isPortInUse`）、`265-273`（`spawnDaemon`）、`275-289`（`runDaemon` 错误分支）、`291-311`（`main`）、`LightMDKit/stop.bat:6-7`、`LightMDKit/stop.sh:5-6`

### 3.2 双击 `lightmdkit.exe` 弹出命令行窗口

**现象**：双击 `LightMDKit/dist/lightmdkit.exe` 时弹出一个黑色控制台窗口；或反过来——服务像是起来了但看不到任何输出、出问题无从下手。

**可能原因**

| # | 原因 | 判断依据 |
|---|------|---------|
| 1 | exe 仍是 **CUI 子系统**（`pkg` 默认产出 `SUBSYSTEM_WINDOWS_CUI = 3`） | 补丁脚本检测到子系统为 3 时会改写为 GUI（`scripts/set-windows-gui.js:38, 45-50`）；已打过补丁会直接输出 `Already WINDOWS_GUI subsystem.`（`LightMDKit/scripts/set-windows-gui.js:40-43`） |
| 2 | 重新打包时**漏跑补丁** | `pkg` 产出新 exe 会覆盖已打补丁的文件；只有 `npm run build:win` 用 `&&` 串起了"打包 + 补丁"（`LightMDKit/package.json:9`），单独执行 `pkg .` 不会打补丁 |
| 3 | 补丁执行失败 | `EXE not found`（路径不对，脚本默认 `dist/lightmdkit.exe`，可用 `argv[2]` 指定，`LightMDKit/scripts/set-windows-gui.js:4-9`）；exe 正在运行导致 `fs.writeFileSync` 抛 `EBUSY/EPERM`（`LightMDKit/scripts/set-windows-gui.js:50`） |
| 4 | 打包产物不是合法 PE 文件 | `Invalid PE file: missing PE signature`（`LightMDKit/scripts/set-windows-gui.js:18-21`）或 `Unexpected optional header magic`（`LightMDKit/scripts/set-windows-gui.js:28-31`）→ 说明 pkg 打包失败或文件被截断 |

**排查步骤**
1. 直接运行补丁脚本看输出：`node LightMDKit/scripts/set-windows-gui.js dist/lightmdkit.exe`
2. 输出 `Changed subsystem to WINDOWS_GUI` → 之前确实没打补丁
3. 输出 `Already WINDOWS_GUI subsystem.` → 补丁已生效，若仍弹黑窗，确认双击的是不是同一个 exe（例如发布包里还有一份旧的）
4. 报 `EXE not found` / `Invalid PE file` → 先修复打包流程（`npm run build:win`）
5. 报 `EBUSY`/`EPERM` → 先完全退出正在运行的 LightMDKit（见 3.1 停止方式）再执行

**解决方案**
1. 统一用 `npm run build:win` 打包（`LightMDKit/package.json:9`），不要手动只跑 `pkg`
2. 打包完成后确认补丁输出为 `Changed subsystem to WINDOWS_GUI: <path>`（`LightMDKit/scripts/set-windows-gui.js:52`）
3. **理解代价**：切到 GUI 子系统后没有控制台，`console.log/console.error` 全部无处输出，加上守护进程 `stdio:'ignore'`（`LightMDKit/server.js:266-271`），exe 形态**完全没有日志**。任何"服务起不来/行为异常"的排查都必须切回源码模式前台启动（第 0 节）
4. 若被安全软件回滚过 exe，需要重新打补丁并加白名单

**源码位置**：`LightMDKit/scripts/set-windows-gui.js:4, 6-9, 14, 18-21, 28-31, 34-50, 52`、`LightMDKit/package.json:9`

### 3.3 浏览器不支持文件夹选择（`showDirectoryPicker` 缺失）

**现象**：点击左侧"📁 加载文件夹..."后，状态栏红字提示 `浏览器不支持文件夹选择，请使用 Chrome 或 Edge`（`app.js:1236`），不弹出任何对话框。

**可能原因**

| # | 原因 | 判断依据 |
|---|------|---------|
| 1 | 非 Chromium 内核浏览器（Firefox / Safari） | `window.showDirectoryPicker` 为 `undefined` → 命中前置检查（`app.js:1235-1238`） |
| 2 | **非安全上下文**：用 `http://<局域网IP>:3456` 或 `http://<主机名>:3456` 访问 | File System Access API 只在 secure context 暴露；`localhost`/`127.0.0.1` 被浏览器视为安全，局域网 IP **不是** → 同样为 `undefined`。Console 执行 `[isSecureContext, typeof window.showDirectoryPicker]` 可确认 |
| 3 | Chromium 版本过旧（File System Access API 需 Chrome/Edge 86+） | Console 检查 `navigator.userAgent` |
| 4 | 内嵌 WebView / 企业策略禁用该 API | Console 中该函数缺失，且不受浏览器版本影响 |

**排查步骤**
1. Console 执行：`[isSecureContext, typeof window.showDirectoryPicker, location.origin]`
2. `location.origin` 不是 `http://localhost:3456` → 基本可判定为原因 2
3. `isSecureContext` 为 `false` → 原因 2；为 `true` 但仍无该函数 → 原因 1/3/4
4. 确认页面是由程序自动打开的（`openBrowser()` 打开的是 `http://localhost:3456`，`LightMDKit/server.js:226, 233-249, 301, 309`），排除用户手工输入了 IP

**解决方案**
1. 使用 Chrome / Edge 打开 <http://localhost:3456>（**不要**用局域网 IP、机器名访问）
2. 需要在别的机器上访问时，当前代码不含 HTTPS 支持，需自行加 HTTPS 反向代理（非安全上下文问题无法通过配置绕过）
3. 服务端虽然实现了 Windows 专用的 `POST /api/select-folder`（`LightMDKit/server.js:19-94`），但**前端没有把它作为降级回退**：`selectFolder()` 只依赖 `showDirectoryPicker`（`app.js:1234-1253`）。在必须用非 Chromium 浏览器的场景，只能另行调用该接口（详见 [API索引](./API索引.md) 与 [外部接入指南](../外部接入指南.md)）

- 在系统对话框点"取消"：状态栏短暂显示 `已取消`（`app.js:1258-1259`）——**这是正常行为，不是故障**

**可能原因**

| # | 原因 | 判断依据 |
|---|------|---------|
| 1 | 用户取消（`AbortError`） | `selectFolder()` 显式区分：`e.name === 'AbortError'` → `已取消`；其它异常走 `setStatus(e.message, 'error')`（`app.js:1244-1250`） |
| 2 | 目录（含递归子目录）里确实没有 `.md`/`.markdown` | 文件计数 `#file-count` 为 0（`app.js:1001-1004`）；扩展名判定见 `app.js:175-178`（大小写不敏感，`.MD` 可用） |

| 5 | 选择的目录不可读（权限、OneDrive/网盘占位文件、受控文件夹访问） | `dirHandle.entries()` 抛异常，`e.message` 被写到状态栏（`app.js:1244-1250`） |
| 6 | 选择的路径被系统对话框当作"文件"或无效路径 | 前端不复核路径，直接 `loadFolderHandle` |

**排查步骤**
1. 先看空态文案区分处境：`当前目录下没有找到 Markdown 文件`（已加载目录但为空，`app.js:1027-1029`）vs `暂无内容，请先加载文件夹`（从未加载过，`app.js:1029`）
2. 用资源管理器确认目录内容与扩展名（是否 `.md` 被存成 `.txt`、是否文件名是 `xxx.md.bak`）
3. Console 复现并看异常：`await window.showDirectoryPicker({mode:'readwrite'})`，观察抛出的 `name`（`AbortError` / `NotAllowedError` / `SecurityError`）
4. 若目录很大：确认目标文件深度是否 ≤ 6、总数是否可能超过 3000（见 3.5）
5. 点一次「刷新」（`app.js:1277-1342`）确认不是"加载后未重扫"

**解决方案**
1. 取消对话框属预期行为，无需处理；`updateLoadFolderButton()` 会把按钮文案恢复（`app.js:1251, 509-515`）
2. 目录为空：换一个包含 md 的目录；或把文档移出 `dist`/`build`/`node_modules` 等被跳过目录
3. 扩展名问题：把文件改回 `.md` / `.markdown`
4. 权限问题：换一个当前用户可读写的目录；OneDrive 未下载到本地的"仅在线"文件也可能读取失败
5. 需要展示深层文档：加载更深一层的目录作为根（见 3.5 解决方案）

### 3.5 文件列表里看不到子目录中的文件

**现象**：某个子目录里的 `.md` 没有出现在左侧文件列表；点「刷新」后仍然看不到；`#file-count` 数量比预期少。

**可能原因**

| # | 原因 | 判断依据 / 限制值 |
|---|------|------------------|
| 1 | **深度超限**：`SCAN_MAX_DEPTH = 6`，`collectMarkdownFiles()` 在 `depth > 6` 时直接返回，不再深入 | `app.js:87, 221`。根为第 0 层，最多深入到第 6 层子目录 |
| 2 | **数量超限**：`SCAN_MAX_FILES = 3000`，达到上限后停止收集 | `app.js:88, 221, 231`。收集顺序 = 每层按名称升序（`app.js:238`）后按目录逐层铺平（`flattenByDirectory`，`app.js:203-225`），超出部分被**静默截断**，不报错 |
| 3 | **目录被跳过**：`SCAN_SKIP_DIRS` 里的目录名一律不下钻 | `app.js:90-92, 233-235`：`node_modules`、`.git`、`.svn`、`.hg`、`.idea`、`.vscode`、`dist`、`build`（本项目自带 `dist/`，若把文档放进去就会"消失"） |
| 4 | **扩展名不符**：只收集 `.md` / `.markdown` | `app.js:175-178, 236-238`（`.MD` 大写可用，`.md.txt` 不行） |
| 5 | 未重新扫描 | 新增文件后需点「刷新」（会重扫，`app.js:1301`）或重新加载文件夹（`app.js:1209`） |
| 6 | 过滤框有残留关键字 | 结果为空时提示 `没有匹配的文件`（`app.js:1043-1049`）；按 Esc 清空（`app.js:1839-1845`） |
| 7 | 符号链接 / 目录联接（junction）指向外部目录 | Chromium 对目录句柄的符号链接支持不一致（**需进一步确认**） |

**排查步骤**
1. 先排除最易误判的一条：清空过滤框（Esc），看 `#file-count` 是否变化
2. 数一数缺失文件的**相对深度**：`a/b/c/d/e/f/x.md` 是第 6 层（可见），再深一层就不可见
3. 查路径中是否有目录名命中跳过列表（尤其 `dist`、`build`）
4. 若目录很大，怀疑 3000 上限：把目标子目录单独作为根加载一次，看文件是否出现（出现即命中数量/深度限制）
5. 用 Console 交叉验证：直接在 Console 里对同一句柄做一次递归列举，与页面列表对比

**平台/来源差异（重要，容易张冠李戴）**

| 来源 | 扫描实现 | 是否递归 |
|------|---------|---------|
| 前端文件列表（浏览器选目录 / 拖入文件夹 / 刷新） | `collectMarkdownFiles()`（`app.js:234-259`） | **递归**，但受 6 层 / 3000 个 / 跳过规则限制 |
| 服务端 `POST /api/load` | `fs.readdirSync()` 单层过滤（`LightMDKit/server.js:118-127`） | **不递归**：只返回目录**顶层**的 `.md`，子目录文件一律不返回 |
| 服务端 `GET /api/file`、`POST /api/refresh` | 按指定路径读单文件（`LightMDKit/server.js:171-224`） | 与目录扫描无关 |

**解决方案**
1. 把文档目录挪浅（≤ 6 层）或直接加载更深一层的目录作为根（根变了，相对深度自然变小）
2. 大仓库：把文档目录单独加载，避开 3000 上限；或临时把 `SCAN_MAX_FILES` 调大（`app.js:92`，代价是扫描变慢、界面卡顿）
3. 把文档移出 `dist` / `build` / `node_modules` 等跳过目录
4. 调用服务端 `/api/load` 的程序要注意它**不递归**（`LightMDKit/server.js:118-127`），需要子目录文件请自行遍历或用前端
5. 刷新后新增文件会有提示：`目录已刷新，发现 N 个新文件`（`app.js:1332-1336`）

**源码位置**：`LightMDKit/public/app.js:91-96, 193-244（核心 220-244）`、`LightMDKit/server.js:118-127`

### 3.6 编辑后内容没保存 / 自动保存失效

**现象**
- 编辑后切回浏览或刷新，内容回到修改前；状态栏出现 `保存失败: xxx`（`app.js:1549`）
- 现代模式下编辑几秒后内容"变回去"，或之后不再自动保存
- 状态栏出现 `当前文件来源不支持写回保存`（`app.js:1537-1539`）

**可能原因**

| # | 原因 | 判断依据 |
|---|------|---------|
| 1 | **来源不可写（拖入的单个文件）**：`initFromDropParam` 在没有目录句柄时用 `{ getFile: ... }` 伪造句柄（`app.js:2062-2064`），该对象没有 `createWritable` → `saveCurrentFile` 直接抛错（`app.js:1536-1540`） | 状态栏报 `当前文件来源不支持写回保存`（句柄无 `createWritable`） |
| 2 | **权限不足**：`createWritable()` 抛 `NotAllowedError`（用户拒绝写权限、目录只读、文件带只读属性、被其它程序独占） | `app.js:1542-1550` 捕获后 `保存失败: <message>`；目录选择时用的是 `mode:'readwrite'`（`app.js:1241`），但权限仍可能被用户在弹窗中拒绝 |
| 3 | **自动保存静默停止（最隐蔽）**：定时器每 3s 触发一次（`AUTOSAVE_INTERVAL_MS = 3000`，`app.js:95, 917-928`），**首次失败即 `stopAutosave()`**（`app.js:1559-1563`）；若提示在 3 秒内被自动清空（`setStatus` 的定时清理，`app.js:167-172`），用户可能什么都没看到，之后再也不保存 | 状态栏 `保存失败: xxx` 只闪现 3 秒，之后不再出现任何保存动作 |
| 4 | **自动保存从未启动**：定时器只在进入编辑态时启动（传统模式 `app.js:1723`、现代模式 `app.js:1665`、启动时若偏好为现代模式 `app.js:2116-2119`）；回调开头还有 `if (!isEditMode) return` 守卫（`app.js:1557`） | 磁盘文件 mtime 长时间不变，且全程没出现过 `已保存` |
| 5 | 现代模式因 CodeMirror 未初始化而被拒 | `编辑器未就绪，无法进入现代模式`（`app.js:1664`）；若 localStorage 存的是 `modern` 但 CodeMirror 失败，启动时会静默退回传统模式（`app.js:2138-2145`） |
| 6 | **刷新/切换文件覆盖了未落盘的改动** | `renderFile()` 在编辑态无条件 `cmEditor.setValue(currentMarkdownText)`（`app.js:1114-1132`）→ 编辑器内容被磁盘内容顶掉 |
| 7 | 保存到了另一个同名文件 | 见 3.14 |

**排查步骤**
1. 看状态栏与 Console：保存失败路径会先 `console.error(e)`（`app.js:1548`），Console 里能看到完整异常名（`NotAllowedError` / `TypeError` 等）
2. 判断文件来源：看顶栏 `#folder-label`——单文件拖入时其 `title` 为"浏览器安全限制，无法自动定位到文件所在目录"（`app.js:2072`），说明没有目录句柄
3. 触发一次**非静默**保存以便看到提示：编辑 → 点「浏览」（`app.js:1690-1698` 调用 `saveCurrentFile()`）
4. 到磁盘核对文件修改时间是否变化（`Get-Item <file> | Select LastWriteTime`）
5. 自动保存是否仍活着：修改内容后等 5 秒，再观察状态栏/磁盘；若首次失败过一次即被停掉，需重新进入编辑态才会重启定时器

**解决方案**
1. 拖入的单文件：改用「📁 加载文件夹」选择其所在目录后打开（句柄来自 `showDirectoryPicker({mode:'readwrite'})`，`app.js:1241`，具备写能力）
2. 权限问题：重新选择文件夹并在浏览器权限提示中允许写入；检查文件只读属性、是否被 Typora/Word/同步盘占用
3. 自动保存停了：切一次编辑态（浏览 → 编辑，或传统 ↔ 现代）会重新 `startAutosave()`（`app.js:1723, 1003`），并先按第 1 步定位首次失败原因
4. 重要内容不要只依赖 3 秒自动保存：用「浏览」按钮触发一次显式保存并确认状态栏 `已保存`（`app.js:1546）
5. 编辑中不要按「刷新」——它会用磁盘内容覆盖编辑器（`app.js:1114-1132`、`1277-1342`）

| 7 | href 含 `#` 或 `?`：查询串与锚点会被截断（`app.js:1502` 的 `href.split(/[?#]/)[0]`）→ 目标名可能因此对不上 | — |

**排查步骤**
1. DevTools → Elements 找到该 `<a>`，读出真实 `href`
2. 点击后看状态栏：**完全没有提示** → 命中 `loadFile()` 的静默返回（`app.js:1257-1258`）；出现 `读取文件...` 后报错 → 是读取阶段失败（走 `app.js:1271-1274`）
3. 看地址栏是否变成 `http://localhost:3456/xxx.md` → 说明未被拦截，走了浏览器默认跳转（原因 1/2）
4. 核对目标能否在左侧文件列表里找到（匹配规则：大小写不敏感、`\` 与 `/` 等价、可省 `./`，`app.js:182-184`）
5. 若是锚点：把侧边栏切到「目录」视图再点一次——能跳即命中原因 3

1. 链接写成**相对于当前文件**的同目录 / 子目录路径（`./a.md`、`sub/a.md`），不要用 `../`（当前实现不解析上级目录）

3. 锚点：切到「目录」视图让标题补上 id（临时绕过）；根治需在渲染后统一生成 heading id（当前代码只在目录视图下做，属功能缺口）
4. 需要支持 `../`、跨目录跳转、非 md 文件时，属功能增强而非配置问题（改动点：`app.js:182-184` 的归一化与 `1352-1518` 的点击处理）
5. 现代模式下点击链接无效属预期，切换回传统模式浏览

### 3.9 现代模式下 `1~100` 显示异常 / 删除线问题

**现象**（两层，需分别定位）
- **预览 / 传统模式**：`范围 1~100、2~5` 被渲染成 `范围 1<del>100、2</del>5`（历史缺陷，见 `feature-todo.md` 第 5 条，已在 `3bbca34` 修复）
- **现代模式编辑器**：范围里的两个 `~` 及其之间的文字被加上删除线、甚至两个 `~` 被隐藏，显示成 `1100、25`

**机制与现状（理解后可做回归验证）**

| 层 | 机制 | 位置 |
|----|------|------|
| 预览渲染 | marked 12 的默认 `del` 规则是 `^(~~?)`——**单个 `~` 也算定界符**（`node_modules/marked/lib/marked.cjs:1170`）。项目用 `patchStrikethrough()` 覆盖 `tokenizer.del`，只认 `~~`；不匹配时返回 `undefined`（**不会**回退到内置规则，字符按普通文本输出，`md-render.js:167-188`） | `md-render.js:158-197` |
| 编辑器 | CM5 的 markdown mode 把单个 `~` 当删除线 → 构造 CodeMirror 时显式关闭 `strikethrough: false`（`app.js:117`）；真正的 `~~…~~` 由 `refreshStrikeMarks()` 用 `markText` 标注 `cm-md-strike` / `cm-md-strike-mark`（`app.js:432-456`），样式在 `style.css:934-952` | `app.js:117, 420-444`（`mode.strikethrough:false` + `markText` 标注） |
| 一致性 | 两处正则形状一致：`REAL_STRIKE_RE`（`app.js:428`）与 `DOUBLE_TILDE_DEL`（`md-render.js:164`） | `app.js:424`、`md-render.js:164`（两处正则形状一致） |

**实测结果**（用项目自带 `renderMarkdown` + marked 12.0.2 跑出，可作为回归基线）

| 输入 | 输出 | 结论 |
|------|------|------|
| `范围 1~100、2~5 与 3~7 之间` | `<p>范围 1~100、2~5 与 3~7 之间</p>` | 正常，不再被渲染成删除线 |
| `这是 ~~删除~~ 文字` | `这是 <del>删除</del> 文字` | 正常 |
| `这是 ~~~三个~~~ 波浪线` | 原样输出 | 定界符紧邻 `~` 不满足 `[^\s~]` 条件 |
| `~~ a ~~` | 原样输出 | 定界符内侧有空格不构成删除线 |
| `~~这里是\n跨行的删除线~~` | `<del>这里是<br>跨行的删除线</del>` | **跨行仍会成对**，而编辑器 `refreshStrikeMarks()` 按行遍历（`app.js:436-455`）不会标注 → 编辑器与预览**表现不一致**（已知差异） |
| 表格内 `1~2` / `~~x~~` | `1~2` 正常 / `<del>x</del>` | 正常 |

**可能原因（出现异常时）**

| # | 原因 | 判断依据 |
|---|------|---------|
| 1 | `md-render.js` 补丁未生效 | 补丁依赖 `marked.use`，且用 `WeakSet` 去重（`md-render.js` 的 `patchStrikethrough`）；`marked` 现为本地锁定版本 `12.0.2`（`index.html:144`），不再是浮动的 CDN 版本 |
| 2 | 浏览器缓存了旧脚本（`index.html:112` 的 `?v=5` 未升） | 见 3.12 |
| 3 | 现代模式样式未生效（`index.html:19` 的 `?v=25` 未升，或容器缺 `live-preview` 类） | `live-preview` 由 `applySurface()` 添加（`app.js:1624`），样式规则在 `style.css:700-1002` |
| 4 | CodeMirror 未初始化，回退 textarea → 现代模式即时渲染整体不可用 | `app.js:162-165`、`1664` |

**排查步骤**
1. 在页面 Console 里直接验证渲染层：`MdRender.renderMarkdown('范围 1~100、2~5', marked)`，对比实测表
2. DevTools → Network 确认 `md-render.js?v=5`、`style.css?v=25` 加载的是最新内容（`index.html:19, 96`）
3. 现代模式下选中范围内文字，用 Elements 面板确认是否带 `cm-md-strike` 类 → 带类说明是标注/CSS 问题，不带类说明是 CM5 mode 配置问题
4. 光标移到该行：现代模式会还原源码（`.CodeMirror-activeline` 规则，`style.css:900-911`），可确认实际字符

**解决方案**
1. 渲染层异常：确认 `md-render.js` 已更新（`renderMarkdown` 内部会先执行 `patchStrikethrough`，`md-render.js:190-197`），并升级 `?v=5`
2. 样式层异常：升级 `index.html:19` 的 `?v=25` 后硬刷新（Ctrl+F5）
3. 跨行 `~~` 的不一致是已知限制；若要完全对齐需把 `refreshStrikeMarks()` 改为跨行扫描（**需进一步确认**实现方式与性能影响）

### 3.12 静态资源缓存导致改动不生效

**现象**：改了 `public/app.js` / `style.css` / `md-render.js`（或服务端逻辑），刷新页面后行为没变，像"改动没生效"。

**可能原因**

| # | 原因 | 判断依据 |
|---|------|---------|
| 1 | **跑的是打包后的 exe（最常见）**：`pkg` 打包时把 `public/**/*` 作为 assets 固化进 exe（`package.json:11-18`），运行时 `express.static(path.join(__dirname, 'public'))`（`server.js:14`）指向的是**快照内**的副本 → 修改源码目录的 `public/` 永远不会生效，必须重新 `npm run build:win`（`package.json:9`） | 任务管理器里进程名是 `markdownlite.exe` 而不是 `node.exe` |
| 2 | **浏览器缓存**：`index.html` 用查询串做版本号——`style.css?v=46`（`index.html:29`）、`md-render.js?v=5`（`index.html:145`）、`app.js?v=82`（`index.html:146`）。改了文件却没升版本号时，同一 URL 可能命中浏览器内存/磁盘缓存 | Network 面板该资源 Size 列显示 `(memory cache)` 或 `(disk cache)` |
| 3 | Express 静态资源默认缓存策略：`express.static` 未传任何 options（`server.js:14`），默认 `Cache-Control: public, max-age=0` + ETag / Last-Modified。`max-age=0` 下浏览器通常会带 `If-None-Match` 回源校验，源文件变了应能拿到新内容；但若中间有反向代理/网关，可能命中网关缓存（**需进一步确认**部署环境） | 响应头为 `Cache-Control: public, max-age=0` 且带 ETag（未配置自定义缓存头） |
| 4 | HTML 自身的缓存控制靠 meta（`index.html:6-8` 的 `no-cache, no-store, must-revalidate`）。meta 只对当前文档生效，且不能覆盖真实响应头；Express 未对 HTML 单独设置缓存头 | 页面源码里有该 meta，但响应头里并没有 `no-cache`（两者不能互相覆盖） |
| 5 | 本地三方库（`vendor/` 下的 CodeMirror / Mermaid / marked / github-markdown-css）被缓存：这些文件也带 `?v=N`（`index.html:20, 28, 136-144`），升级库时换了文件却忘了把该行 `?v=` 加一，浏览器会继续用旧的 | 请求 URL 指向 `localhost:3456/vendor/...`，且响应 Size 列是 `(disk cache)` |
| 6 | 服务端 `server.js` 修改后没重启（守护进程不会热重载） | 进程启动时间早于文件修改时间 |

**排查步骤**
1. 先确认运行形态：任务管理器里是 `lightmdkit.exe` 还是 `node.exe`？是 exe 就必须重新打包（原因 1）
2. DevTools → Network → 勾选 **Disable cache** 后刷新，看目标资源的 Status 与 Size：
   - `(memory cache)` / `(disk cache)` → 命中浏览器缓存（原因 2）
   - `304` → 已回源校验且认为未变（检查是不是改的不是同一份文件）
   - `200` → 拿到新内容，问题在别处
3. 对照磁盘内容：`curl -s http://localhost:3456/app.js` 输出与 `public/app.js` 里的新代码是否一致（例如 `curl -s http://localhost:3456/app.js | grep "<刚改的关键字>"`）
4. 确认服务进程的启动时间晚于代码修改时间（否则重启服务）

**解决方案**
1. 源码模式：改完 `public/` 下任意文件后，**同步把 `index.html` 对应 `?v=` 数字加 1**（`index.html:29, 145, 146`；改 `vendor/` 下的库则加该行自己的 `?v=`），再 Ctrl+F5 硬刷新
2. exe 形态：`npm run build:win` 重新打包（别忘了 GUI 子系统补丁，见 3.2），退出旧进程后再运行新 exe
3. 排查期临时手段：DevTools 勾选 Disable cache；或 Network 面板右键请求 → Clear browser cache
4. 改了 `server.js` 必须重启服务：`stop.bat` / `pkill -f "node server.js"` 后重新启动（守护进程不会自动加载新代码）

**源码位置**：`public/index.html:6-8, 29, 145, 146`、`server.js:14`、`package.json:9, 11-18`

### 3.13 三方库加载失败（离线 / 资源缺失 / vendor 目录不完整）

> **状态：已于 2026-10-08 修复。** 三方库不再走 CDN，全部本地化在 `public/vendor/`，
> 正常情况下不会再有"库加载不出来"。本节保留下来，用于排查 **vendor 资源缺失**这类新形态
> 的故障（有人删了/改了 `vendor/` 下的文件、打包漏了资源、手改 `index.html` 引错路径）。

**现象**：页面能打开但排版错乱；点击文件后正文空白或只显示一段纯文本 + 「Markdown 渲染库（marked）未加载」的提示；点「现代模式」提示 `编辑器未就绪，无法进入现代模式`；Console 有 `CodeMirror/Mermaid init failed, falling back to textarea:`。

**原因**：`index.html` 引用的 `vendor/` 资源没加载出来（404 / 路径写错 / 文件缺失），对应的全局变量变成 `undefined`：

| 缺失的库 | 后果 | 依据 |
|---------|------|------|
| `marked` | 客户端渲染退化为纯文本：`renderMarkdownHtml` 检测到 `window.marked` 缺失，返回提示 + `<pre>` 原文（内容不丢，也不再抛错）。**2026-10-08 之前**没有这层兜底，会直接抛 `Cannot read properties of undefined (reading 'parse')`（`md-render.js:194` 的 `marked.parse(...)`），报障原文就是它 | `app.js` 的 `renderMarkdownHtml`；`md-render.js:194` |
| `CodeMirror` | 初始化抛错被兜住，`cmEditor = null` → 回退 textarea，传统模式仍可用；现代模式被拒；若 localStorage 偏好为 modern，启动时静默退回传统 | `app.js` 的 CodeMirror 初始化 try/catch |
| `mermaid` | 图表不渲染，其余功能正常（`typeof mermaid === 'undefined'` 直接返回） | `app.js` 的 `renderMermaid` |
| `github-markdown-css` | 排版退化（无报错） | `index.html` 引用的 vendor 样式 |

**排查步骤**：
1. DevTools → Network 过滤 `vendor/`，看哪些请求 404 或失败
2. Console 执行 `[typeof marked, typeof CodeMirror, typeof mermaid]`，缺哪个补哪个
3. 对照 `public/vendor/` 磁盘目录，确认文件在且路径与 `index.html` 的引用一致（大小写敏感）

**解决方案**：把缺的文件补回 `public/vendor/`（上游文件与其目录位置见 `index.html` 顶部的注释），改了 exe 形态要重新 `npm run build:win`。**不要**改回 CDN —— 本工具部署环境可能不能上网，CDN 正是这次故障的成因。

**源码位置**：`public/index.html`（vendor 引用与策略注释）、`public/app.js`（`renderMarkdownHtml`、`renderMermaid`、CodeMirror 初始化）、`public/md-render.js:194`

### 3.14（补充）打开子目录中的文件时内容可能串位（同名文件）

**现象**（**已修复**，保留此条是为说明根因，便于后续改动时不再踩同一个坑）：根目录与子目录存在同名 `.md`（如 `a.md` 与 `sub/a.md`），从文件列表打开 `sub/a.md` 时，曾显示/保存为根目录那个 `a.md` 的内容。

**原因与依据**：`renderFile()` 曾用**文件名（不含子目录）**从目录根重新获取句柄：`currentFolderHandle.getFileHandle(fileEntry.name)`；而 `collectMarkdownFiles()` 写入的 `entry.name` 只有 basename，只有 `entry.path` 才包含子目录前缀。根目录存在同名文件时，`getFileHandle(name)` 会成功返回**根目录那个文件**的句柄，随后 `handle.getFile()` 读到的就是它；若根目录没有同名文件则抛 `NotFoundError`，被 catch 忽略并回退到扫描时的正确句柄 —— 因此**只在同名场景暴露**。

**排查步骤**
1. 确认"内容不对"的文件在根目录是否有同名文件
2. 对照文件列表分组标题（渲染自 `entry.path`）与 `currentFile`
3. 在根目录与子目录各放一个同名 `a.md`、内容不同，打开子目录那个实测确认

**解决方案**：**已在 `LightMDKit/public/app.js:1100-1112` 修复** —— 重取句柄改为沿 `entry.path` 用 `/` 拆段、逐级 `getDirectoryHandle` 再 `getFileHandle`，任一步失败则回退到扫描时的句柄。另建议避免在根目录与子目录放同名文档，以减少选择歧义。

**源码位置**：`LightMDKit/public/app.js:1100-1112`（修复点）、`234-258`（`entry.path` 的来源）

## 6. 排障最佳实践

### 6.1 排障原则

- **先定形态，再谈根因**：源码模式 / exe / 守护进程三者的资源来源与日志能力完全不同（第 0 节）。"改了不生效""没有日志"八成是形态问题，而不是代码问题。
- **先拿日志，再猜原因**：默认启动方式把日志丢进了黑洞（`stdio:'ignore'` + GUI 子系统），务必先用 `LIGHTMDKIT_DAEMON=1` 前台启动复现一次。
- **区分"设计如此"与"缺陷"**：取消选择显示 `已取消`、现代模式不显示图片、拖入单文件不定位目录、锚点链接在文件列表视图下不跳——都是当前实现下的预期行为，先排除这些再定位缺陷。
- **保留现场**：报错前先截图状态栏、复制 Console 堆栈、记下 DevTools Network 里该资源的 URL 与状态码。
- **对照可复现基线**：`~` 相关的回归直接用 3.9 的实测表比对；文件扫描相关问题先量深度与数量（6 层 / 3000 个）。

### 6.2 预防措施

- **改前端资源必升版本号**：`index.html:19/96/97` 的 `?v=` 是唯一的缓存失效手段，建议纳入提交前自检清单。
- **打包后必跑 GUI 补丁**：统一用 `npm run build:win`（`LightMDKit/package.json:9`），不要单独执行 `pkg .`；打包完确认输出 `Changed subsystem to WINDOWS_GUI`（`LightMDKit/scripts/set-windows-gui.js:52`）。
- **不要用 `taskkill /F /IM node.exe`**（`LightMDKit/stop.bat:7`）：会杀掉机器上所有 Node 程序，建议改为按 PID 精确结束，或让服务写入 PID 文件。
- **补充日志能力**：当前无日志文件、无级别、无请求记录。建议至少为服务端错误与前端上报增加文件日志，否则 exe 形态的问题基本无法事后追溯。
- **文档同步**：README 中"再次启动时提示选择「重新运行」/「显示访问 URL」"与当前 `main()` 实现不符（`LightMDKit/server.js:291-311` 无交互提示）；历史文档中出现的 `findPidByPort()` 在当前源码中**不存在**（同名函数已不在 `server.js` 中）。改动启动逻辑后请同步更新 README 与知识库，避免排障时被误导。
- **仓库体积**：`dist/lightmdkit.exe`（约 40 MB）当前被 git 跟踪，每次打包都会产生大对象，建议评估改为 `.gitignore` + 发布产物。
- **已知边界写进使用说明**：6 层 / 3000 文件扫描上限（`app.js:87-88`）、跳过目录清单（`app.js:90-92`）、不解析 `../`（`app.js:182-184`）、服务端 `/api/load` 不递归（`LightMDKit/server.js:118-127`）——建议在 README 的"使用说明"里明确，减少误报为故障。
