## 阅读前：系统边界与关键前提

理解本文档的流程前，需要先明确三条决定性的前提 —— 7 个流程中 6 个的行为都由它们推导而来。

**前提 1：业务流程几乎全部发生在前端。**
`LightMDKit/public/app.js` 是一个单文件 IIFE（2154 行），承载了加载、浏览、编辑、保存、模式切换、拖放、刷新的全部逻辑。服务端 `LightMDKit/server.js` 只做三件事：托管 `public/` 静态资源、启动/复用本地服务进程、对外暴露 4 个 HTTP 接口（当前无前端调用方）。后两者见 [服务端 API 渲染链路](#服务端-api-渲染链路)；至于这 4 个接口本身的定义与调用方式，见 [API 索引](../技术知识库/API索引.md)。

**前提 2：文件的读写走浏览器 File System Access API，不走 HTTP。**
经检索确认，`LightMDKit/public/app.js` 与 `LightMDKit/public/index.html` 中**没有任何 `fetch(` / `XMLHttpRequest` / `/api/` 调用**。`LightMDKit/server.js` 中定义的 4 个接口（`POST /api/select-folder`、`POST /api/load`、`GET /api/file`、`POST /api/refresh`，分别位于 `LightMDKit/server.js:19`、`:97`、`:171`、`:199`）**当前界面不会触发它们**，属于为外部集成保留的通道。因此：

- 目录选择 = `window.showDirectoryPicker()`（浏览器原生对话框），不是服务端的 PowerShell 对话框；
- 文件读取 = `FileSystemFileHandle.getFile()`；
- 文件保存 = `FileSystemFileHandle.createWritable()`。

**前提 3：目录、文件都通过「句柄（handle）」而非「路径字符串」访问磁盘。**
句柄由浏览器授权持有，所以应用内存里同时维护着两套标识：

| 标识 | 形态 | 用途 |
|------|------|------|
| `handle` | `FileSystemDirectoryHandle` / `FileSystemFileHandle` | 真正读写磁盘 |
| `path` | 相对目录根的 `/` 分隔字符串，如 `业务知识库/核心业务领域.md` | 列表高亮、链接匹配、历史栈、IndexedDB 传递 |

`name` 只是文件名（`核心业务领域.md`），**在递归扫描后不再唯一** —— 不同子目录可以有同名文件，所以凡是「定位一个文件」的代码必须用 `path`。这条约束在流程 2、3、6、7 里反复出现，是本项目最容易写错的地方。

**核心状态变量清单**（均定义在 `LightMDKit/public/app.js` 顶部）：

| 变量 | 行号 | 含义 |
|------|------|------|
| `currentFiles` | `:28` | 扫描结果数组 `[{ name, path, handle }]`，已按目录铺平排序 |
| `currentFile` | `:30` | 当前文件的相对路径（即 entry.path） |
| `currentMarkdownText` | `:32` | 当前文件的 Markdown 原文，编辑时随 `change` 事件实时更新 |
| `headingOffsets` | `:34` | 标题 id → 原文字符偏移，供编辑态目录跳转使用 |
| `isEditMode` | `:40` | 是否处于编辑态（现代模式恒为 true） |
| `currentMode` | `:43` | `'traditional'` / `'modern'`，启动时从 localStorage 恢复 |
| `currentFolderHandle` | `:99` | 当前目录句柄，为 null 表示只打开了单个文件 |
| `fileHistory` | `:97` | 返回栈，存的是 `path` 字符串 |
| `imageUrlCache` | `:101` | 图片相对路径 → objectURL |

`mode: 'readwrite'` 是编辑模式能落盘的前提 —— 若只申请 `read`，后续 `createWritable()` 会抛 `NotAllowedError`。

**Step 3：准备目录状态** (`LightMDKit/public/app.js:1216`)

```javascript
async function loadFolderHandle(dirHandle, preferredFileName) {
  clearImageCache();
  currentFolderHandle = dirHandle;
  folderLabel.textContent = dirHandle.name;
  folderLabel.title = dirHandle.name;

  const files = await collectMarkdownFiles(dirHandle);

  currentFiles = files;
  currentFile = null;
```

`clearImageCache()` (`LightMDKit/public/app.js:1164`) 会 `URL.revokeObjectURL` 掉上一目录的全部图片缓存，避免换目录后内存里堆着旧 blob。此函数被 `selectFolder` 与拖放新标签页 (`initFromDropParam`) 共用，所以清理逻辑写在这里而不是入口处。

**Step 4：递归扫描** (`LightMDKit/public/app.js:234`)

```javascript
async function collectMarkdownFiles(dirHandle, prefix = '', depth = 0, out = []) {
  if (depth > SCAN_MAX_DEPTH || out.length >= SCAN_MAX_FILES) return out;

  const entries = [];
  for await (const [name, handle] of dirHandle.entries()) {
    entries.push({ name, handle });
  }
  // 让扫描顺序稳定（entries() 的顺序由系统决定），同名排序与旧逻辑一致
  entries.sort((a, b) => a.name.localeCompare(b.name));

  for (const entry of entries) {
    if (out.length >= SCAN_MAX_FILES) break;
    const { name, handle } = entry;
    if (handle.kind === 'directory') {
      if (SCAN_SKIP_DIRS.has(name)) continue;
      await collectMarkdownFiles(handle, prefix + name + '/', depth + 1, out);
    } else if (isMarkdownName(name)) {
      out.push({ name, path: prefix + name, handle });
    }
  }

  // 只在最外层收尾，避免每层递归都重排一次
  if (depth === 0) return flattenByDirectory(out);
  return out;
}
```

三道阈值/过滤规则（常量定义在 `LightMDKit/public/app.js:91`）：

```javascript
const SCAN_MAX_DEPTH = 6;
const SCAN_MAX_FILES = 3000;
const SCAN_SKIP_DIRS = new Set([
  'node_modules', '.git', '.svn', '.hg', '.idea', '.vscode', 'dist', 'build',
]);
```

- 深度：`depth > SCAN_MAX_DEPTH` 才返回，根目录 `depth = 0`，因此最多进入第 6 层子目录；
- 数量：达到 3000 后逐个 `break`，**已扫到的照常可用，不做任何报错或提示**；
- 目录黑名单：`node_modules`、`.git`、`.svn`、`.hg`、`.idea`、`.vscode`、`dist`、`build`（对文档浏览无意义，同时避开 pkg 打包产物噪声）。

文件类型判定 `isMarkdownName` (`LightMDKit/public/app.js:179`) 取最后一个 `.` 后的扩展名，`md` / `markdown` 均接受（大小写不敏感）。

**Step 5：按目录铺平** (`LightMDKit/public/app.js:207`)

```javascript
function flattenByDirectory(files) {
  const root = { dirs: new Map(), files: [] };
  for (const file of files) {
    const slash = file.path.lastIndexOf('/');
    const segments = slash === -1 ? [] : file.path.slice(0, slash).split('/');
    const baseName = slash === -1 ? file.path : file.path.slice(slash + 1);
    let node = root;
    for (const seg of segments) { /* 建树 */ }
    node.files.push({ baseName, entry: file });
  }

  const out = [];
  (function walk(node) {
    node.files.sort((a, b) => a.baseName.localeCompare(b.baseName));
    for (const f of node.files) out.push(f.entry);
    const names = [...node.dirs.keys()].sort((a, b) => a.localeCompare(b));
    for (const name of names) walk(node.dirs.get(name));
  })(root);
  return out;
}
```

这里**不能**简单地 `files.sort((a, b) => a.path.localeCompare(b.path))`。函数上方注释（`LightMDKit/public/app.js:203`）解释了原因：`/` 的码点是 `0x2F`，汉字「深」是 `0x6DF1`，整路径排序会让 `sub/deep/d.md` 排在 `sub/note.md` 前面，于是子目录文件与父目录文件交替插花，而 `renderFileList` 是按「目录段变化就插入一个分组标题」渲染的 —— 同一个目录会被拆成好几段、标题重复出现。按树逐层铺平（先本目录的文件，再依次进子目录）保证每个目录**只出现连续的一段**。

过滤框的匹配口径与链接匹配共用 `normalizePathForMatch`（`LightMDKit/public/app.js:186`，反斜杠归一为 `/`、去前导 `./`、转小写），所以输入 `业务/核心` 能命中 `业务知识库/核心业务领域.md`。

**Step 7：渲染文件内容** (`LightMDKit/public/app.js:1098`)

```javascript
async function renderFile(fileEntry) {
  let handle = fileEntry.handle;
  // 从目录重新获取句柄，避免句柄级缓存导致读取到旧内容。
  // 子目录文件必须按 path 逐级取 —— 只传文件名会命中根目录的同名文件
  const relativePath = fileEntry.path;
  if (currentFolderHandle && typeof relativePath === 'string' && relativePath) {
    try {
      const segments = relativePath.split('/').filter(Boolean);
      let dir = currentFolderHandle;
      for (let i = 0; i < segments.length - 1; i++) {
        dir = await dir.getDirectoryHandle(segments[i]);
      }
      handle = await dir.getFileHandle(segments[segments.length - 1]);
    } catch (e) {
      // 忽略错误，回退到传入的句柄
    }
  }
  const file = await handle.getFile();
  const text = await file.text();
  currentMarkdownText = text;
  headingOffsets = parseHeadingOffsets(text);
  const html = MdRender.renderMarkdown(text, marked);
  contentEl.innerHTML = html;
  if (currentMode !== 'modern') await resolveImages();
  if (isEditMode) { /* 同步编辑器内容并保留光标/滚动位置 */ }
  applySurface();
  renderToc();
  // 只更新高亮不重建列表：过滤框里正打字时重建会让输入框失焦
  updateActiveFileItem();
  renderMermaid();
}
```

渲染管线是 `MdRender.renderMarkdown(text, marked)` (`LightMDKit/public/md-render.js:190`)，依次做三件事：`mergeTableCells`（合并跨行表格单元格，用 `<br>` 表示换行）、`preserveIndent`（把非结构行的前导空白转成 `&nbsp;`，保住缩进）、`patchStrikethrough`（只认 `~~` 删除线，见 [现代模式即时编辑](#现代模式即时编辑)），最后交给 `marked.parse(..., { gfm: true, breaks: true })`。

图片解析 `resolveImages()` (`LightMDKit/public/app.js:1173`) 把相对路径的 `<img src>` 换成 objectURL：跳过 `http(s):` / `data:` / `blob:` / `#` / `//` 开头的绝对引用，按 `/` 拆段逐级 `getDirectoryHandle` 支持子目录，命中缓存则复用，失败时保留原 `src` 并 `console.warn`。

注意 `renderFileList()` 与 `showEmptyState()` 是**两条独立的空状态路径**：

- `loadFolderHandle` 先调 `renderFileList()`（`:742`），此时 `currentFiles` 为空 → 侧栏显示「当前目录下没有找到 Markdown 文件」；
- 再调 `showEmptyState('该目录下没有找到 Markdown 文件')`（`:745`），主内容区显示空状态，同时 `tocEl` 被写成「暂无内容」。

两处措辞不同（「当前目录下没有找到」vs「该目录下没有找到」），它们服务的是不同区域，不要为了「统一文案」把二者合并。

### 加载注意事项

1. **`currentFile` 不只是「文件名」。** 它保存的是 `target.path || target.name`（`:753`）。凡是拿它去 `getFileHandle()` 或做相等比较的地方，都必须考虑 `path` 带子目录前缀（如 `a/b.md`）的情形 —— `getFileHandle('a/b.md')` 会直接抛错。
2. **`renderFile` 的句柄重取已改为按 `path` 解析（曾按文件名，已修复）。** 旧实现传的是 `fileEntry.name`（文件名，不含子目录），对子目录文件必然抛 `NotFoundError` 并落回原句柄；更隐蔽的是若根目录恰好存在同名文件，`getFileHandle` 会**成功**并返回根目录那个文件，导致读错内容、进而写错文件。现已改为沿 `entry.path` 用 `/` 拆段、逐级 `getDirectoryHandle` 再 `getFileHandle`（`LightMDKit/public/app.js:1100-1112`），任一步失败仍回退到扫描时的句柄。新增按路径解析的逻辑时请沿用这个逐级下钻的写法。
3. **扫描上限是静默的。** 超过 3000 个文件或 6 层深度时不会提示用户「只扫了一部分」。如果产品上需要提示，改动点在 `LightMDKit/public/app.js:235` 与 `:235`（需要把「被截断」这一信息带出递归）。
4. **`SCAN_SKIP_DIRS` 是硬编码的 `Set`。** 用户若确实需要浏览 `dist/` 下的 md（例如构建产物里的文档），当前实现无法做到 —— 没有配置项可绕过。
5. **空目录会保留 `currentFolderHandle`。** 因此「更换文件夹...」按钮文案（`updateLoadFolderButton`，`:513`）判的是句柄而非文件数：加载一个空目录后按钮仍显示「更换文件夹...」，这是符合预期的。
6. **`renderFileList` 每次都是全量重建。** 过滤框 `input` 事件直接调它（`:1168`），3000 个文件时每次输入都会重建整段 DOM。若要做性能优化，应先在这里下手。

**Step 1：唯一入口 `renderToc`，运行时被装饰过** (`LightMDKit/public/app.js:2130-2135`)

视图守卫的含义：**侧栏停在「文件列表」页时，`renderToc()` 整个是空操作**，不会重建目录、也不会重建滚动监听。调用点共 4 处：`renderFile`（`:662`，每次读文件后）、`setMode`（`:1037`）、`setSidebarView`（`:1147`，切回目录视图时）、`scheduleLivePreviewRefresh`（`:409`，现代模式编辑防抖 300ms 后）。

**Step 2：标题来源分叉** (`LightMDKit/public/app.js:937`)

```javascript
renderToc = function () {
  // 现代模式下 contentEl 是隐藏的且可能已经过期，目录改从编辑器原文实时解析
  if (currentMode === 'modern') {
    renderTocFromSource();
    return;
  }
  tocEl.innerHTML = '';
  const headings = contentEl.querySelectorAll('h1, h2, h3, h4, h5, h6');
  if (headings.length === 0) {
    tocEl.innerHTML = '<p class="toc-empty">当前文件没有标题目录</p>';
    return;
  }

  // 统一重新生成 heading id，确保与 parseHeadingOffsets 生成的键一致
  const usedIds = new Set();
  headings.forEach(h => {
    h.id = generateHeadingId(h.textContent || '', usedIds);
  });
```

传统模式会**重写 DOM 上的 heading id**：`marked` 自己生成的 id 与 `generateHeadingId`（`:267`）规则不同，而编辑态跳转要靠 `headingOffsets[h.id]` 查偏移表，两边必须同构，所以这里统一重算一次。

现代模式走 `renderTocFromSource()`（`:364`），标题来自 `getHeadingsCached`（`:342`）—— 按全文缓存解析结果，避免每次光标移动都 O(n) 重新解析。

驱动源按模式分两套：

### 目录注意事项

1. **三个 id 生成点必须永远保持同构。** DOM（传统模式 `:950-954`）、`headingOffsets`（`parseHeadingOffsets`，`:289`）、`extractHeadings`（`:330`）都调用 `generateHeadingId` + 独立 `Set` + 按文档顺序遍历，因此天然对齐 —— 这也正是注释里写明「id 生成与 parseHeadingOffsets 完全同构」的原因（`:327-329`）。改 `slugify` 或去重规则时，这三处必须一起改，否则会出现「点目录跳到了错误的位置」。
2. **`renderToc` 的声明与赋值分离（曾为隐式全局，已修复）。** 现在 `LightMDKit/public/app.js:44` 有 `let renderToc;` 声明，直到文末 `LightMDKit/public/app.js:2131-2135` 才赋值为带视图守卫的版本，全项目只此一处赋值。因此不要在别处再写 `renderToc = ...` —— 那会覆盖装饰链、让视图守卫失效。
3. **不要直接调用被包装的那个实现（`renderTocContent`）。** 它绕过了视图守卫，会让「文件列表」视图下的每次读文件都重建目录；正确入口始终是 `renderToc()`。
4. **两套高亮机制互斥且由模式决定**，不要同时启用：现代模式下 `contentEl` 是隐藏的（`display: none`），IntersectionObserver 对它不会产生有意义的可见性变化。
5. **空状态有两套文案，含义不同。** `showEmptyState` 会把 `tocEl` 写成「暂无内容」（`:1095`），表示「还没加载文件」；「当前文件没有标题目录」（`:379`、`:945`）表示「已加载但文档里没有标题」。

**Step 3：路径解析** (`LightMDKit/public/app.js:1269`)

```javascript
async function loadFile(path) {
  const entry = findEntryByPath(path);
  if (!entry) return;
  setStatus('读取文件...');
  try {
    currentFile = entry.path || entry.name;
    // 传统模式切换文件时自动切回浏览模式；现代模式保持常驻编辑态
    if (isEditMode && currentMode !== 'modern') {
      stopAutosave();
      isEditMode = false;
      applySurface();
    }
    await renderFile(entry);
    updateActiveFileItem();
    setStatus('文件已加载', 'success');
  } catch (e) {
    console.error(e);
    setStatus(e.message, 'error');
  }
}
```

**Step 4：路径匹配** (`LightMDKit/public/app.js:192`)

```javascript
function findEntryByPath(path) {
  if (!path) return null;
  const byPath = currentFiles.find(f => f.path === path);
  if (byPath) return byPath;
  const target = normalizePathForMatch(path);
  return currentFiles.find(f => f.path === undefined && f.name === path)
    || currentFiles.find(f => normalizePathForMatch(f.path || f.name) === target)
    || null;
}
```

三级匹配策略，逐级放宽：

1. **精确匹配 `f.path === path`** —— 正常路径，`currentFiles` 由扫描产生，`path` 来自 `renderFileList` / 历史栈 / 链接解析，口径一致；
2. **旧结构兼容** `f.path === undefined && f.name === path` —— 兼容 `initFromDropParam` 早期只塞 `{ name, handle }` 的形态；
3. **归一化匹配** `normalizePathForMatch` —— 处理 `./sub/a.md`、`sub\a.md`、`SUB/A.MD` 三种写法。

`normalizePathForMatch` (`LightMDKit/public/app.js:186`) 只有三件事，但它是全应用的路径比较口径：

```javascript
return String(path || '').replace(/\\/g, '/').replace(/^\.\//, '').toLowerCase();
```

**Step 5：渲染与高亮** —— `renderFile(entry)` 完成后调用 `updateActiveFileItem()` (`LightMDKit/public/app.js:1820`)：

```javascript
function updateActiveFileItem() {
  fileListEl.querySelectorAll('.file-item').forEach(item => {
    item.classList.toggle('active', item.dataset.path === currentFile);
  });
}
```

它只改 class、**不重建列表**。这一区分很重要：`renderFile` 会调用它（`:664`），而 `renderFileList` 会重建 DOM；如果这里也重建，用户在过滤框打字时每读一个文件就会让输入框失焦。

### 切换注意事项

1. **不要用 `name` 做文件比较。** `currentFiles` 里 `path` 才是唯一键；`name` 在跨子目录时会碰撞。历史栈、`dataset.path`、`currentFile`、IndexedDB 记录全部统一用 `path`。
2. **`loadFile` 的失败不会回滚 `currentFile`。** `currentFile` 在 `try` 的第一行就被改（`:786`），之后 `renderFile` 抛错只进 `catch` 提示，不会恢复旧值 —— 结果是「`currentFile` 指向 B，正文仍是 A」。若要让失败可恢复，需要把赋值挪到 `renderFile` 成功之后。
3. **传统模式下编辑态切换文件会丢弃未保存的修改吗？不会 —— 但要看清顺序。** `loadFile` 只是 `stopAutosave()` 并退回浏览态（`:789`），**并不调用 `saveCurrentFile`**。数据得以保留是因为自动保存每 3 秒会先落盘一次（见 [编辑并保存文档](#编辑并保存文档)）；用户若在 3 秒内就点了另一个文件，这段修改只存在于 `currentMarkdownText`，随后被 `renderFile` 覆盖。
4. **`findEntryByPath` 的归一化分支会退化为「按 name 匹配」。** 第三级用了 `f.path || f.name`，对正常扫描结果不成问题，但要清楚这里的比较是大小写不敏感的。
5. **无提示的静默失败应被视为缺陷而非设计。** 若产品上要给反馈，改动点在 `LightMDKit/public/app.js:1271`，改完注意别影响 `openFileFromList` 的前置判断。

`getTopVisibleHeadingId()` (`LightMDKit/public/app.js:313`) 用 `getBoundingClientRect()` 在渲染后的 `<h1>~<h6>` 中找第一个 `rect.top >= wrapperTop - 10` 的标题（10px 容差），返回其 id；拿到后用 `headingOffsets[id]` 换算成字符偏移，再转行号 `setCursor` + `scrollIntoView`（`:1085`）。退出编辑态时反过来用 `lastViewHeadingId` 恢复滚动（`:1065`）—— 这是「编辑前后视线不跳走」的关键，改动编辑器初始化时不要破坏 `headingOffsets` 与 DOM `id` 的同构关系。

**Step 3：保存** (`LightMDKit/public/app.js:1553`)

```javascript
async function saveCurrentFile(silent = false) {
  if (!currentFile) return;
  // currentFile 是相对路径，同名文件可能分布在多个子目录，必须按 path 取
  const entry = findEntryByPath(currentFile);
  if (!entry) return;
  if (!entry.handle || typeof entry.handle.createWritable !== 'function') {
    const msg = '当前文件来源不支持写回保存';
    if (!silent) setStatus(msg, 'error');
    throw new Error(msg);
  }
  try {
    const writable = await entry.handle.createWritable();
    await writable.write(cmEditor ? cmEditor.getValue() : editorEl.value);
    await writable.close();
    currentMarkdownText = cmEditor ? cmEditor.getValue() : editorEl.value;
    if (!silent) setStatus('已保存', 'success');
  } catch (e) {
    console.error(e);
    setStatus('保存失败: ' + e.message, 'error');
    throw e;
  }
}
```

四个要点：

- **`silent` 参数**：自动保存传 `true`，只写盘不刷状态栏；手动保存传 `false`，成功后显示「已保存」。
- **必须先 `close()`**：`createWritable()` 返回的是临时文件写入流，只有 `close()` 才真正提交到磁盘；漏掉 `close()` 会导致「看起来保存成功但文件没变」。
- **抛异常而非吞掉**：`:924` 与 `:935` 都 `throw`，让 `startAutosave` 能据此停表。
- **失败提示重复**：`catch` 里已经 `setStatus`，调用方 `toggleEditMode` 不再提示 —— 这是有意的分工。

**Step 4：自动保存** (`LightMDKit/public/app.js:1576`)

```javascript
function startAutosave() {
  if (autosaveTimer) return;
  autosaveTimer = setInterval(async () => {
    if (!isEditMode) return;
    try {
      await saveCurrentFile(true);
    } catch (e) {
      // 自动保存失败已在 saveCurrentFile 内提示，停止定时器避免反复报错
      stopAutosave();
    }
  }, AUTOSAVE_INTERVAL_MS);
}
```

`if (autosaveTimer) return;` 让 `startAutosave` 幂等，可被多处安全调用。失败即停表是关键设计：拖入的单文件没有可写句柄，若不停表就会每 3 秒弹一次「当前文件来源不支持写回保存」。

**Step 5：编辑器内容实时回写内存** (`LightMDKit/public/app.js:149`)

### 保存注意事项

1. **两种来源天然不可写。** 一是 `initFromDropParam` 的单文件分支（`LightMDKit/public/app.js:2084`），它的 handle 是手工构造的 `{ getFile: async () => record.fileBlob }`，**根本没有 `createWritable`**；二是浏览器只授予 `read` 权限的目录。两种情况都会走到 `:921` 的分支。若要让拖入的单文件可保存，需要给用户一个「另存为」路径（`showSaveFilePicker`），当前实现没有。
2. **`saveCurrentFile` 有两条「静默 return」路径**（`:917` 无 `currentFile`、`:920` 无 `entry`）。它们不会 `throw`，所以调用方 `await` 之后会认为「保存成功」。刷新目录后当前文件被移除的场景正是如此（见 [刷新目录](#刷新目录)）。
3. **自动保存是「整文件覆盖写」，不是增量写。** 每 3 秒把编辑器全文写入磁盘，大文件会有明显 IO。若要改成「有变更才写」，需要在 `cmEditor.on('change')` 处打脏标记。
4. **保存不写临时文件、不做原子替换。** `createWritable()` 默认直接改目标文件，写入过程中崩溃会留下半截文件。这是浏览器 API 的默认行为，不是本项目的疏漏；若需要原子性，得显式用 `keepExistingData: false` 之外的方案自建备份。
5. **`currentMode === 'modern'` 时编辑器内容由自动保存负责落盘。** 传统模式下用户点「浏览」是一次强制保存点；现代模式没有这个动作，切走模式时靠 `setMode` 里的 `saveCurrentFile(true)`（`LightMDKit/public/app.js:1672`）兜底。
6. **别把 `stopAutosave` 挪到 `saveCurrentFile` 内部。** 它被 `toggleEditMode`、`setMode`、`loadFile` 分别按需调用，一旦内聚到保存函数里，现代模式（常驻编辑态）就会保存一次就停表。

**Step 5：删除线标注** (`LightMDKit/public/app.js:436`)

```javascript
const REAL_STRIKE_RE = /~~(?=[^\s~])([\s\S]*?[^\s~])~~(?=[^~]|$)/g;

function refreshStrikeMarks() {
  clearStrikeMarks();
  if (currentMode !== 'modern' || !cmEditor) return;
  const lineCount = cmEditor.lineCount();
  for (let i = 0; i < lineCount; i++) {
    const text = cmEditor.getLine(i);
    if (text.indexOf('~~') === -1) continue;
    REAL_STRIKE_RE.lastIndex = 0;
    let m;
    while ((m = REAL_STRIKE_RE.exec(text)) !== null) {
      const start = m.index;
      const end = start + m[0].length;
      // 内容加删除线；前后两对 ~~ 单独标注以便隐藏（三个区间互不重叠）
      strikeMarks.push(cmEditor.markText({ line: i, ch: start + 2 }, { line: i, ch: end - 2 },
        { className: 'cm-md-strike' }));
      strikeMarks.push(cmEditor.markText({ line: i, ch: start }, { line: i, ch: start + 2 },
        { className: 'cm-md-strike-mark' }));
      strikeMarks.push(cmEditor.markText({ line: i, ch: end - 2 }, { line: i, ch: end },
        { className: 'cm-md-strike-mark' }));
    }
  }
}
```

为什么不用 CodeMirror 5 自带的删除线？构造处注释（`LightMDKit/public/app.js:116`）给了根因：

```javascript
// strikethrough 必须关掉：CM5 自带的删除线把单个 ~ 也当定界符
// （mode/markdown/markdown.js 里 `ch === '~' && stream.eatWhile(ch)` 后直接切换状态），
// 于是「1~100、2~5」这种范围写法会被误判成删除线，两个 ~ 还会被当成标记隐藏掉，
// 直接显示成「1100、25」。真正的 ~~...~~ 改由 markText 单独标注（见 refreshStrikeMarks）。
mode: { name: 'gfm', highlightFormatting: true, strikethrough: false },
```

同一规则在渲染侧由 `LightMDKit/public/md-render.js` 的 `patchStrikethrough` 实现（`LightMDKit/public/md-render.js:167`），覆盖 marked 的 `del` 分词器，只认双波浪线。**编辑侧的 `REAL_STRIKE_RE` 与渲染侧的 `DOUBLE_TILDE_DEL` 必须保持同构**，否则会出现「编辑器里看着是删除线、预览里不是」的错位。

**Step 6：编辑时的防抖刷新** (`LightMDKit/public/app.js:413`)

### 模式注意事项

1. **传统模式的标记隐藏依赖 CSS，不是 JS 换 DOM。** 全部规则挂在 `.live-preview` 作用域下（`LightMDKit/public/style.css:700` 起），类由 `applySurface()` 切换。改样式时不要写成不带 `.live-preview` 前缀的全局规则，否则传统模式也会被隐藏标记。当前行例外：`.live-preview .CodeMirror-activeline .cm-formatting { … }`（`LightMDKit/public/style.css:900`）把光标所在行的标记恢复显示，这正是「Typora 式」的来源。
2. **`styleActiveLine` 不能在传统模式开。** 它会给当前行加 `.CodeMirror-activeline`，基础样式 `codemirror.css` 的 `.CodeMirror-activeline-background{background:#e8f2ff}` 会刷一层蓝底。项目在 `LightMDKit/public/style.css:716` 显式用 `.CodeMirror:not(.live-preview)` 关掉了它作为兜底。
3. **`theme: 'github'` 是有意为之的空主题。** `codemirror@5` 的 npm 包 `theme/` 目录里没有 github，`LightMDKit/public/index.html` 顶部注释（`LightMDKit/public/index.html:11`）说明：保留它只是为了让容器带 `cm-s-github` 类，从而不启用 `cm-s-default` 的默认配色；真正的配色来自 `LightMDKit/public/style.css` 的 `.content-wrapper .cm-*`。
4. **`refreshStrikeMarks` 是 O(行数) 的。** 每次模式切换、每次 300ms 防抖都会重扫全文 `markText`。几千行的文档会有可感知的开销 —— 若要优化，先跳过不含 `~~` 的行（已经做了，`:430`）。
5. **`renderToc` 是运行时被「装饰」的闭包变量**（`LightMDKit/public/app.js:2130-2135`）。它先在文件顶部声明（`:38` 的 `let renderToc;`），文中赋值为重建目录的实现，文末再被重绑定为带视图守卫的版本；`renderTocContent` 保存着被装饰的原始实现：

   ```javascript
   const renderTocContent = renderToc;
   renderToc = function () {
     if (sidebarView !== 'toc') return;
     renderTocContent();
     setupTocObserver();
   };
   ```

   这意味着**只有当侧栏停在「目录」页时，`renderToc()` 才真的重建目录**；停在「文件列表」页时它是空操作。这个赋值曾因缺少声明而成为隐式全局，已在 `LightMDKit/public/app.js:44` 补上 `let renderToc;` 修复；改动时仍要注意：若在别处也写 `renderToc = ...`，会把装饰链覆盖掉。
6. **现代模式的目录高亮不走 IntersectionObserver。** `setupTocObserver` 在 `currentMode === 'modern'` 时直接 `return`（`LightMDKit/public/app.js:2114`），改由 `cmEditor.on('cursorActivity')` 驱动（`:148`）。两套机制不要混用。

**Step 3：逐项处理** (`LightMDKit/public/app.js:1982`)

```javascript
async function handleDroppedItems(dataTransfer) {
  let opened = 0;
  const tasks = [];
  for (const item of Array.from(dataTransfer.items)) {
    if (item.kind !== 'file') continue;
    tasks.push((async () => {
      let handle = null;
      if (item.getAsFileSystemHandle) {
        try {
          handle = await item.getAsFileSystemHandle();
        } catch (e) {
          handle = null;
        }
      }
      // 拖入的是文件夹：新标签页直接加载整个目录
      if (handle && handle.kind === 'directory') {
        await openDropInNewTab({ folderHandle: handle });
        opened++;
        return;
      }
      const file = handle ? await handle.getFile() : item.getAsFile();
      if (!file || !isMarkdownName(file.name)) return;
      // matchCurrentFolder 命中时返回该文件在已加载目录中的相对路径，
      // 新标签页据此把文件列表高亮定位到子目录里的对应文件
      const matchedPath = await matchCurrentFolder(handle);
      const record = {
        fileName: file.name,
        filePath: matchedPath || null,
        fileHandle: handle || null,
        fileBlob: handle ? null : file,
        folderHandle: matchedPath ? currentFolderHandle : null,
      };
      await openDropInNewTab(record);
      opened++;
    })());
  }
  await Promise.all(tasks);
  if (opened === 0) {
    setStatus('仅支持拖入 .md / .markdown 文件或文件夹');
  }
}
```

几个关键设计：

- **`tasks` 数组 + `Promise.all`**：每个 item 独立起一个 async 任务，多文件同时拖入时并行处理（会开多个标签页）。
- **`fileBlob` 与 `fileHandle` 二选一**：拿到句柄时存句柄（不需复制文件内容），拿不到时退化为存 `File` 对象本体（可结构化克隆）。这两个字段互斥，靠 `handle ? null : file` 保证。
- **`folderHandle` 只在命中已加载目录时才存**：见下一步。
- **`opened === 0` 的兜底提示**：覆盖了「拖入 .txt」「拖入图片」等场景。

**Step 4：判断拖入文件是否在当前目录内** (`LightMDKit/public/app.js:1949`)

```javascript
async function matchCurrentFolder(fileHandle) {
  if (!currentFolderHandle || !fileHandle) return false;
  for (const f of currentFiles) {
    try {
      if (await f.handle.isSameEntry(fileHandle)) return f.path || f.name;
    } catch (e) { /* 比较失败时忽略 */ }
  }
  return null;
}
```

`isSameEntry` 是 File System Access API 提供的句柄同一性判断，比路径字符串比较更可靠。命中时返回**相对路径**（`f.path`），这正是新标签页能把列表定位到子目录里那个文件的原因。

单文件分支的 `{ getFile: async () => record.fileBlob }` 是一个**鸭子类型句柄** —— 只实现了 `getFile`，没有 `createWritable`。这直接决定了拖入的单文件不可保存（见 [保存注意事项](#保存注意事项)）。

**Step 7：过期清理** (`LightMDKit/public/app.js:1922`)

```javascript
async function idbPurgeExpired() {
  try {
    const db = await openDropDb();
    await new Promise((resolve) => {
      const tx = db.transaction(DROP_STORE, 'readwrite');
      const store = tx.objectStore(DROP_STORE);
      const now = Date.now();
      store.openCursor().onsuccess = (e) => {
        const cursor = e.target.result;
        if (cursor) {
          const v = cursor.value;
          if (!v || !v.ts || now - v.ts > DROP_TTL_MS) cursor.delete();
          cursor.continue();
        }
      };
      tx.oncomplete = () => { db.close(); resolve(); };
      tx.onerror = () => { db.close(); resolve(); };
    });
  } catch (e) { /* IndexedDB 不可用时忽略 */ }
}
```

每次页面启动时执行（`LightMDKit/public/app.js:2152`），TTL 24 小时。注释解释了为什么可以放心清理：文件句柄权限只随浏览器会话保留，记录本就无需长期存在。

### 拖放注意事项

1. **句柄权限不跨会话。** 记录里存的是句柄，浏览器重启后权限失效，`getFile()` 会抛 `NotAllowedError`（此时新标签页已关闭、记录靠 TTL 清理）。不要把这条路子当作「持久化的最近打开列表」来用。
2. **`matchCurrentFolder` 的返回值类型不统一**：无目录句柄或无 fileHandle 时返回 `false`，正常未命中返回 `null`。调用处只用了真值判断（`matchedPath || null`），目前无害，但若将来要区分「没有目录」与「不在目录内」，需要先统一返回类型。
3. **拖入文件与拖入文件夹是两条体验差异极大的路径。** 只拖文件时用户会看到「浏览器限制未定位所在目录，可手动『加载文件夹』」的提示（`LightMDKit/public/app.js:2098`）；这是浏览器安全模型的硬限制，不是可以修的 bug，修改文案时要保留这个信息量。
4. **一次拖入多个 md 会开多个标签页。** `tasks` 里的每个任务各自 `window.open`。浏览器通常会拦截多弹窗，被拦截的会退化为状态栏链接。
5. **`idbPut` / `idbGet` 每次都开关一次数据库连接**（`db.close()` 在事务回调里）。调用频率低，可接受；若要高频读写需复用连接。
6. **`record.fileBlob` 存的是 `File` 对象本体。** 大文件（如几十 MB 的 md 与内嵌内容）会被完整复制进 IndexedDB，24 小时后才清理。这是「拿不到句柄」时的必要代价。

### 跳转注意事项

1. **`fileHistory` 只有内存、没有持久化，且换目录时不清空。** `loadFolderHandle` 不重置它（`LightMDKit/public/app.js:1216` 起）。切换文件夹后旧路径全部失效，此时点「← 返回」会走 `findEntryByPath` 未命中 → 静默 return（见 [切换注意事项](#切换注意事项)），表现为「返回按钮点了没反应」。若要修，应在 `loadFolderHandle` 里清栈并 `updateBackButton()`。
2. **返回栈可能记录到已删除的文件。** 与上一条同源。刷新目录后文件被删除，历史栈不会同步清理。
3. **`..` 相对路径不被支持。** 判定逻辑只做前缀拼接，不做路径折叠。若产品需要支持，改动点在 `LightMDKit/public/app.js:1349` 附近，需要引入真正的路径归一化（折叠 `.` 与 `..`），并注意此时不能再用「拼接后查找」的方式。
4. **同名的根目录文件与子目录文件不会混淆**，这是本流程的核心价值：`baseDir + hrefPath` 得到的是相对根的完整路径，`findEntryByPath` 的第一级是精确 `path` 比较。不要为了让查找更"宽松"而把这一级删掉。
5. **链接目标不存在时没有任何提示。** 非 md 链接（如 `.pdf`）会走浏览器默认跳转，而指向不存在 md 的链接（命中不了任何一级查找）同样走浏览器默认行为 —— 在本地 HTTP 服务下会得到 404。如果希望这类情况有提示，需在未命中的分支里显式判断「看起来像 md 链接」再给状态栏反馈。

**Step 4：刷新触发的重渲染** —— `renderFile` 会从句柄重新 `getFile()`（`LightMDKit/public/app.js:1117`），所以外部编辑器对文件的修改能被读到。`updateActiveFileItem()` 在重建列表之后再执行一次，保证高亮落在正确的项上（`renderFileList` 重建时也按 `currentFile` 加了 `active` 类，这次调用是双保险）。

### 刷新注意事项

1. **编辑态点刷新会丢弃未保存的修改。** `renderFile` 在 `isEditMode` 为真时会把编辑器内容整段替换成磁盘内容（`LightMDKit/public/app.js:1132` 的 `cmEditor.setValue(currentMarkdownText)`，此时 `currentMarkdownText` 已被磁盘内容覆盖）。现代模式下同样成立，而且随后的自动保存还会把这份磁盘内容再写回一次。若要让刷新对编辑态安全，应在编辑态先 `saveCurrentFile()` 或提示用户。
2. **「当前文件已被移除」后 `currentFile` 没有被清空。** `:833` 直接 `return`，`currentFile` 仍是那个已失效的路径。后果是：此后点「刷新」还会再报一次同样的提示（因为 `!currentFile` 判断为假），编辑与保存则因 `findEntryByPath` 返回 null 而静默失效。要修就在 `:833` 前把 `currentFile = null` 并 `applySurface()`。
3. **`imageUrlCache` 在刷新时不清。** 图片文件被替换后仍显示旧图，直到切换目录或换文件夹（`loadFolderHandle` 会清）。若要修，在 `:831` 后调 `clearImageCache()`。
4. **新增统计是净增量。** 若提示文案要精确表达「新增 N / 删除 M」，需要改成分别统计两个集合的差集。
5. **刷新不会重新读取过滤框语义之外的状态。** 侧栏过滤框的值会被 `renderFileList` 重新应用（`:554`），所以刷新后用户视角一致 —— 这也意味着过滤框里若有内容，新增文件可能被过滤掉而"看不见"，但状态栏仍会报出新增数量。

## 服务端 API 渲染链路

> ⚠️ **当前 UI 未调用，为外部集成保留。**
>
> 经代码检索确认，`LightMDKit/public/app.js` 与 `LightMDKit/public/index.html` 中**没有任何 `fetch(` / `XMLHttpRequest` / `/api/` 引用** —— `LightMDKit/server.js` 里的 4 个接口没有任何前端调用方。本文档前面的 7 个流程（加载文件夹、切换与查看文件、编辑并保存、现代模式、拖放、链接跳转、刷新目录）**全部走浏览器 File System Access API，一个字节都不经过服务端**。

**Step 2：`POST /api/load` 参数校验与目录列举** (`LightMDKit/server.js:97`)

```javascript

  let files = [];
  try {
```

这里是**服务端与前端能力差异最大的一处**：`fs.readdirSync` 只列举一层，子目录里的 Markdown 不会被收录，也没有 `SCAN_SKIP_DIRS` 黑名单与 3000 文件上限。前端用的是递归版 `collectMarkdownFiles`（见 [加载文件夹并浏览文档](#加载文件夹并浏览文档)）。

**Step 3：渲染并返回** (`LightMDKit/server.js:142`)

```javascript

    if (!fs.existsSync(targetFile)) {
      return res.status(404).json({ error: 'File does not exist: ' + targetFile });

      return res.status(400).json({ error: 'Path is not a file: ' + targetFile });
```

**Step 4：两个功能等价的只读接口** (`LightMDKit/server.js:171`、`LightMDKit/server.js:199`)

`GET /api/file` 与 `POST /api/refresh` 的处理体完全一致（校验 → 读盘 → 渲染 → 返回 `{ content, html, path }`），差别只有两点：参数来源（query 的 `path` vs body 的 `filePath`）与 HTTP 方法。之所以是两个接口，是历史命名使然 —— `refresh` 表达的是「前端刷新当前文件」的语义，而前端后来改走文件句柄，两者都已无调用方。

### 服务端注意事项

1. **路径参数没有根目录约束，是一处需要留意的安全面。** `path.resolve(folderPath)` / `path.resolve(filePath)`（`LightMDKit/server.js:104`、`:133`、`:178`、`:206`）之后直接读盘，调用方可以传任意绝对路径（如 `C:\Windows\...`）。由于服务只监听 `localhost` 且当前 UI 不调用这些接口，实际暴露面是「本机其他进程/页面若能访问 3456 端口」。若要把这些接口真正开放给外部集成，应当先加白名单根目录校验。
2. **服务端没有写接口，也没有目录选择之外的状态管理。** 想在外部集成里保存文件，只能拿到 `content` 自己写盘 —— 前端那条链路才具备写回能力（靠浏览器授权）。
3. **`/api/load` 的 `files` 不含子目录。** 若外部工具期望它与前端的文件列表一致（前端是递归的），会得到不同结果。要对齐的话，需要把递归扫描逻辑也搬到服务端。
4. **`/api/file` 与 `/api/refresh` 是重复实现。** 改其中一个的行为（比如加缓存、加参数校验）时，记得另一个也要同步，否则两条等价接口会漂移。
5. **改 `LightMDKit/public/md-render.js` 会同时改掉两条链路的渲染结果。** 这是好事（规则统一），但也意味着服务端 API 的输出格式会随前端渲染需求一起变 —— 若将来有外部工具依赖固定 HTML 结构，需要先评估。
6. **`/api/select-folder` 只支持 Windows**（`:21`），且依赖 `powershell.exe` 存在于 PATH。这条路径在前端已经没有调用方（前端用浏览器原生对话框），属于纯外部集成能力。

### 服务启动与端口复用

同属服务端侧的另一条链路是**进程启动与端口复用** —— 它不经过任何 HTTP 请求，却决定了上面这些接口是否有人监听。它决定了「双击 exe / 运行 `npm start` 之后会发生什么」。

#### 启动执行路径

**Step 1：分流** (`LightMDKit/server.js:291`)

```javascript
async function main() {
  if (process.env[DAEMON_ENV] === '1') {
    runDaemon();
    return;
  }

  const portBusy = await isPortInUse(PORT);

  if (!portBusy) {
    spawnDaemon();
    console.log(`LightMDKit started at ${url}`);
    await sleep(2000);
    openBrowser(url);
    process.exit(0);
  }

  console.log(`\n端口 ${PORT} 已被占用，LightMDKit 可能已在运行。`);
  console.log(`打开访问地址: ${url}`);
  openBrowser(url);
  process.exit(0);
}
```

`DAEMON_ENV = 'LIGHTMDKIT_DAEMON'`（`LightMDKit/server.js:227`）。这个环境变量把同一个入口文件分成两种角色：启动器（打开浏览器后退出）与守护进程（常驻监听）。

**Step 2：端口探测** (`LightMDKit/server.js:251`)

```javascript
function isPortInUse(port) {
  return new Promise((resolve) => {
    const tester = net.createServer()
      .once('error', (err) => {
        resolve(err.code === 'EADDRINUSE');
      })
      .once('listening', () => {
        tester.once('close', () => resolve(false));
        tester.close();
      })
      .listen(port);
  });
}
```

用「试着监听」来探测，而不是连接探测 —— 前者能区分「端口被占用」与「端口开着但对方不是 HTTP 服务」。

**Step 3：拉起守护进程** (`LightMDKit/server.js:265`)

```javascript
function spawnDaemon() {
  const child = spawn(process.execPath, [__filename], {
    detached: true,
    stdio: 'ignore',
    windowsHide: true,
    env: { ...process.env, [DAEMON_ENV]: '1' }
  });
  child.unref();
}
```

`detached` + `unref` 让守护进程脱离启动器的进程树，启动器 `process.exit(0)` 后它继续存活；`windowsHide: true` 配合打包成 GUI 子系统（见 `LightMDKit/package.json` 的 `build:win` 脚本调用 `LightMDKit/scripts/set-windows-gui.js`）实现「双击不弹黑窗」。

**Step 4：监听与端口冲突兜底** (`LightMDKit/server.js:275`)

```javascript
function runDaemon() {
  const server = app.listen(PORT, () => {
    // 服务已在后台运行，不自动打开浏览器，避免重复打开新标签页
  });

  server.on('error', (err) => {
    if (err.code === 'EADDRINUSE') {
      console.error(`Port ${PORT} is already in use.`);
      process.exit(1);
    } else {
      console.error('Server error:', err.message);
      process.exit(1);
    }
  });
}
```

**Step 5：打开浏览器** (`LightMDKit/server.js:233`) —— 按平台分发 `cmd /c start`（Windows）、`open`（macOS）、`xdg-open`（Linux），`detached` + `stdio: 'ignore'` + `unref`，并吞掉 `error` 事件避免抛未捕获异常。

#### 启动注意事项

1. **固定端口 3456，没有端口自增逻辑。** 被占用时直接复用已有实例（假定那就是 LightMDKit）。若 3456 被别的程序占用，用户会被导向那个程序 —— 这是设计取舍，改动点在 `LightMDKit/server.js:297`。
2. **`await sleep(2000)` 是硬编码等待**（`LightMDKit/server.js:302`）。机器慢时守护进程可能还没监听就已经打开浏览器，用户会看到连接失败。若要稳健，应改成轮询端口直到可连接。
3. **服务端 4 个 API 接口当前无调用方。** 它们的能力边界、与前端的差异以及路径未做根目录约束的安全注意点，统一写在 [服务端 API 渲染链路](#服务端-api-渲染链路) 一节，这里不再重复。
4. **静态资源目录是 `public/`**（`LightMDKit/server.js:14`），`dist/` 里打包后的 exe 通过 pkg 的 `assets` 配置把 `public/**/*` 一并带上（见 `LightMDKit/package.json`）。

## 全局共性注意事项

以下四条贯穿多个流程，改任何一处代码前都值得先看一遍。

1. **`path` 是唯一键，`name` 不是。** 出现「定位文件」需求时（列表高亮、链接匹配、历史栈、IndexedDB 记录、保存写回），一律用 `path`。`renderFile` 里重取句柄的调用已按此原则改为沿 `path` 逐级 `getDirectoryHandle` 再取文件（`LightMDKit/public/app.js:1100-1112`）—— 原先按 `name` 取会在根目录存在同名文件时命中错文件，导致读、编辑、保存全作用在错误的文件上，该隐患已消除。
2. **`currentMarkdownText` 是「编辑器的真值」，不是「磁盘的真值」。** 磁盘内容只在 `renderFile` 之后短暂与它一致；编辑器 `change` 会立刻覆盖它。任何需要「磁盘上的内容」的逻辑都应直接 `handle.getFile()`，不要读这个变量。
3. **三处「静默失败」需要留意。** `loadFile` 未命中目标（`:783`）、`saveCurrentFile` 无 entry（`:920`）、文档内链接未命中路径（`:893` → 不 `preventDefault`）。它们目前都没有用户可见提示，是排障时最容易误判为「没反应」的三个点。
4. **前端完全没有 HTTP 数据通道。** 不要试图通过新增 `/api/*` 接口来实现文件操作 —— 读写能力全在 File System Access API 上，服务端看不到任何文件句柄。服务端新增接口只适合做「本地能做的事」（如打开系统对话框、启动外部程序、跨会话保存偏好），不能替代前端已有的读写路径。
