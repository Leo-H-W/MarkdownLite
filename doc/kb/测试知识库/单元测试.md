# 单元测试文档

> 本文档从代码仓库中提取，说明如何编写和运行单元测试。
>
> **本文档的特殊性**：LightMDKit 是一个纯粹的"浏览器端 + 静态服务"项目，**当前没有任何自动化测试**（无测试框架、无测试文件、无 CI）。因此本文档分为两部分：
> - **第一部分（第 1–7 章）**：如实描述测试现状，并给出"若要开始写测试，该从哪切入"的指导。
> - **第二部分（第 8 章）**：**人工验证清单**——在自动化测试缺位的情况下，按功能模块列出的可落地回归验证步骤。
>
> 凡标注「**现状**」的均为已在仓库中核实的事实，标注「**建议**」的为尚不存在、需要新建的内容。

## 4. 测试代码模板

> **现状**：项目**没有任何测试文件可供提取模板**。以下模板为**建议**，基于仓库中真实存在的 `public/md-render.js` 编写，并已在 Node v24.13.0 下实测运行通过。

### 4.1 基础测试模板

**参考源文件**：`LightMDKit/public/md-render.js:1-8`（UMD 包装，支持 Node `require`）、`LightMDKit/public/md-render.js:199`（导出清单）

```javascript
// test/md-render.test.js
const test = require('node:test');
const assert = require('node:assert');
const { marked } = require('marked');
const { renderMarkdown } = require('../public/md-render.js');

test('当文档出现范围写法时应保持原样而非渲染为删除线', () => {
  const html = renderMarkdown('范围 1~100、2~5', marked);
  assert.ok(!html.includes('<del>'), '单个 ~ 不应产生 <del>');
});

test('当使用双波浪线时应渲染为删除线', () => {
  const html = renderMarkdown('~~删除~~', marked);
  assert.ok(html.includes('<del>删除</del>'));
});
```

> 该模板的实测运行结果：`pass 2 / fail 0`。

### 4.2 Mock 使用模板

**现状**：项目**没有任何 Mock 代码**。`md-render.js` 的设计使得大多数场景**无需 Mock**——依赖通过参数注入（`LightMDKit/public/md-render.js:190` 的 `renderMarkdown(markdown, marked)` 接收 `marked` 实例），而非在模块内 `require`。

因此**建议**的"打桩"方式是参数注入而非 Mock 框架：

```javascript
// 用最小替身验证"依赖被正确注入并调用"，不需要 jest.mock
test('renderMarkdown 应把预处理后的文本交给 marked.parse', () => {
  const calls = [];
  const fakeMarked = {
    use: () => {},
    parse: (text) => { calls.push(text); return '<p>stub</p>'; },
  };
  const { renderMarkdown } = require('../public/md-render.js');

  const html = renderMarkdown('  foo\n    bar', fakeMarked);   // 行首缩进会被预处理

  assert.strictEqual(html, '<p>stub</p>');
  assert.strictEqual(calls.length, 1);
  assert.ok(calls[0].includes('&nbsp;'), '缩进应已转换为 &nbsp;');
});
```

> **注意（现状）**：`LightMDKit/public/md-render.js:167-188` 的 `patchStrikethrough` 会调用 `marked.use(...)` **原地修改传入的 marked 实例**，而 `marked` 是模块单例。用 `patchedMarked`（一个 `WeakSet`，`LightMDKit/public/md-render.js:165`）防止重复打补丁，因此**补丁效果会跨测试用例累积**。编写测试时需注意这一点，不要假设每个用例拿到的是"未打补丁"的 marked。

## 5. 如何编写新测试

### 5.1 步骤 1：确认测试对象是否可测

**首先检查目标模块是否能被 Node `require`**。本项目的可测性分成三档：

| 模块 | 可测性 | 原因 |
|-----|-------|------|
| `LightMDKit/public/md-render.js` | ✅ **易测** | UMD 包装（`:1-8`）导出 4 个函数（`:171`），仅依赖注入的 `marked`，无 Node/浏览器 API |
| `LightMDKit/server.js` | ⚠ **中等** | 依赖 `fs`/`child_process`/`express`；且 `main()` 在模块加载时直接执行（`:313`），`require` 会真的启动服务并尝试打开浏览器 |
| `LightMDKit/public/app.js` | ❌ **难测** | 浏览器 IIFE（`:1`），**无任何导出**，依赖 DOM / CodeMirror / Mermaid / File System Access API / localStorage / IndexedDB |

已验证 `md-render.js` 可被 Node 直接加载：

```
$ node -e "console.log(Object.keys(require('./public/md-render.js')).join(', '))"
preserveIndent, mergeTableCells, patchStrikethrough, renderMarkdown
```

> 这也是 `LightMDKit/server.js:7` 的 `require('./public/md-render.js')` 能work的原因——同一份渲染逻辑同时服务浏览器端与 Node 端。

### 5.2 步骤 2：选择推荐参考位置

由于项目无现存测试，**建议**按下表选择被测源码作为参照：

| 参考位置 | 适用于 | 建议的测试切入点 |
|---------|-------|----------------|
| `LightMDKit/public/md-render.js:10-57` (`preserveIndent`) | 纯字符串变换 | 缩进转换、围栏代码块内缩进不被改写、结构性缩进（列表/引用/标题）保持原样 |
| `LightMDKit/public/md-render.js:59-156` (`splitTableCells`/`isDelimiterRow`/`mergeTableCells`) | 多行状态机 | 表格多行单元格合并为 `<br>`、表格边界判定 |
| `LightMDKit/public/md-render.js:158-188` (`patchStrikethrough`) | 分词器补丁 | **单 `~` 不产生 `<del>`**、双 `~~` 产生 `<del>`、重复调用不重复打补丁（`WeakSet`） |
| `LightMDKit/server.js:100-130` (`POST /api/load` 参数校验分支） | HTTP 接口 | 缺少 `folderPath` → 400；目录不存在 → 404；路径是文件 → 400 |
| `LightMDKit/server.js:171-196` (`GET /api/file`) | HTTP 接口 | 缺少 `path` → 400；指向目录 → 400；文件不存在 → 404 |

### 5.3 步骤 3：编写测试

1. 修改测试名为 `当{条件}时应{预期行为}`
2. 准备输入数据（**纯函数优先直接传字符串，无需 fixture 文件**）
3. 注入依赖（参考 `LightMDKit/public/md-render.js:190` 的参数注入写法，而非 Mock 框架）
4. 执行被测代码
5. 断言结果（用 `node:assert` 的 `strictEqual` / `ok` / `throws`）

### 5.4 步骤 4：运行验证

```bash

node --test test/md-render.test.js

# 若已按建议添加 "test": "node --test" 脚本
npm test
```

> **若要为 `server.js` 接口写测试**，需先做可测性改造（**现状：尚未改造**）：
> - 把 `LightMDKit/server.js:313` 的 `main();` 改为 `if (require.main === module) main();`
> - 把 `app`（`LightMDKit/server.js:10`）通过 `module.exports` 导出

## 6. 测试规范

### 6.1 命名规范（建议）

| 项目 | 规范 |
|-----|-----|
| 测试目录 | `test/`（位于项目根，与 `public/`、`scripts/` 平级） |
| 测试文件 | `{源文件名}.test.js`，如 `md-render.test.js` |
| 测试分组 | `describe('{模块或函数名}', () => { ... })` |
| 测试用例 | `test('当{条件}时应{预期行为}', () => { ... })` |
| 否定用例 | `test('当{异常输入}时应{异常行为}', () => { ... })` |

### 6.2 测试结构（建议）

推荐 **AAA 模式**（Arrange-Act-Assert），并显式加注释分段：

```javascript
test('当表格单元格跨行时应合并为同一行并用 <br> 连接', () => {
  // Arrange - 准备输入（表格首格内容跨了两行）
  const input = '| a | b |\n| --- | --- |\n| 第一行\n续行 | 值 |';

  // Act
  const { mergeTableCells } = require('../public/md-render.js');
  const result = mergeTableCells(input);

  // Assert - 续行被并回首格，两行合成一行（注意：行数会减少，不是保持不变）
  assert.strictEqual(result, '| a | b |\n| --- | --- |\n| 第一行<br>续行 | 值 |');
});
```

> 上述断言中的期望字符串已实测验证（输入 4 行 → 输出 3 行）。另附一个已验证的 `preserveIndent` 期望值，可直接用作回归基线——它同时覆盖了"缩进转换"与"结构性缩进豁免"两个分支：
>
> ```javascript
> preserveIndent('  普通文本\n  - 列表项\n  # 标题\n  | 表格 |')
> // => '&nbsp;&nbsp;普通文本\n  - 列表项\n  # 标题\n  | 表格 |'
> //    第 1 行普通文本的缩进被转为 &nbsp;；
> //    后三行分别是列表 / 标题 / 表格，属结构性行，缩进原样保留
> ```

### 6.3 Mock 原则（建议）

- **优先参数注入，而非 Mock 框架**：`md-render.js` 已按此设计（`LightMDKit/public/md-render.js:190`），保持这一风格即可，无需引入 Mock 库。
- **不 Mock 业务逻辑**：`preserveIndent`、`mergeTableCells` 这类纯函数应真实调用，只对输入做变量控制。
- **不 Mock `marked`**：`marked` 是已安装的真实依赖，且 `~` 修复的**正确性只在与真实 marked 12 交互时才成立**（补丁针对的是 marked 12 的内置 `del` 规则，见 `LightMDKit/public/md-render.js:158-163` 的注释）。**若用假 marked，这个 bug 的回归测试会完全失效。**
- **测试隔离注意**：`patchStrikethrough` 修改的是 marked 单例（见 4.2 节说明），涉及该补丁的用例需接受跨用例的补丁累积。

### 6.4 为什么 `app.js` 难测（现状与改造建议）

`LightMDKit/public/app.js` 是一个立即执行函数（`:1` 的 `(function () {` 到 `:1465` 的 `})();`），**不导出任何符号**，且模块级直接执行了 DOM 查询（`:2-22`）与副作用调用（`:1458-1464`）。它依赖以下浏览器专有 API：

| 依赖 | 位置 | 测试障碍 |
|-----|------|---------|
| `document.querySelector` 等 DOM API | `LightMDKit/public/app.js:2-28` | 需 jsdom |
| File System Access API（`showDirectoryPicker`） | `LightMDKit/public/app.js:1254` | 无 Node 实现，必须整体打桩 |
| `FileSystemDirectoryHandle.entries()` | `LightMDKit/public/app.js:238` | 需构造异步迭代器替身 |
| `CodeMirror`（全局变量，来自本地 `vendor/`） | `public/app.js` 的 CodeMirror 初始化处 | 需真实或替身编辑器实例 |
| `mermaid`（全局变量，来自本地 `vendor/`） | `public/app.js` 的 `renderMermaid` | 同上 |
| `localStorage` | `LightMDKit/public/app.js:53` 等 | 需 jsdom 或替身 |
| `IndexedDB` | `LightMDKit/public/app.js:1889-1941` | 需 fake-indexeddb |

> **建议**：与其为 `app.js` 搭 jsdom + 全套 API 替身，**性价比更高的路径是先做小范围重构**——把下列已经是纯函数的逻辑抽到独立模块并导出，即可直接单元测试，同时不影响浏览器行为：
>
> | 待抽取函数 | 当前位置 | 抽出的收益 |
> |---|---|---|
> | `normalizePathForMatch` | `LightMDKit/public/app.js:186-188` | 覆盖反斜杠 / `./` 前缀 / 大小写归一化 |
> | `flattenByDirectory` | `LightMDKit/public/app.js:207-229` | 覆盖"子目录文件不插花、目录标题不重复"这一易错点（`:188-192` 注释记录了一次真实踩坑） |
> | `slugify` / `generateHeadingId` | `LightMDKit/public/app.js:268-287` | 覆盖重复标题的 `-1`/`-2` 去重 |
> | `isMarkdownName` | `LightMDKit/public/app.js:179-182` | 覆盖 `.md`/`.markdown`/大小写 |
> | `parseHeadingOffsets` | `LightMDKit/public/app.js:289-328` | 覆盖标题 → 字符偏移映射（编辑/浏览位置同步的基础） |
>
> 在这些函数被抽出并导出之前，它们的正确性**只能靠第 8 章的人工验证清单保障**。

### 7.3 边界条件测试

**参考**：`LightMDKit/public/md-render.js:10-57`（`preserveIndent` 的边界判定）

该函数最易出错的边界（每条都对应源码中的一次分支判断）：

- 围栏代码块**内**的行首缩进**不应**被转换（`:30-33`）
- 列表项 `- foo` 前的缩进**不应**被转换（`:40-43`，`isStructural` 判定）
- 标题 `# foo` / 引用 `> foo` / 表格 `| foo` 前的缩进**不应**被转换（`:41-46`）

## 9. 与源码核实的差异说明

编写本文档时，以下细节经核实与"想当然的理解"不同，特此记录，避免后续误用：

1. **`POST /api/load` 不是递归扫描**。`LightMDKit/server.js:118-127` 使用的是 `fs.readdirSync`（**仅一层**），不进入子目录。**前端默认并不调用该接口**——它走的是浏览器 File System Access API，由 `LightMDKit/public/app.js:234-258` 的 `collectMarkdownFiles` 做**递归扫描**（含跳过目录与深度/数量上限）。服务端那套 REST API 是"替代或扩展"用途（见 `README.md` 的「服务端 API」小节）。因此验证递归扫描、跳过目录、深度/数量上限时，**必须通过浏览器界面验证，不能通过调用 `/api/load` 验证**。

2. **`md-render.js` 不是完全纯的模块**。`preserveIndent`（`:10`）与 `mergeTableCells`（`:72`）是纯字符串函数，但 `renderMarkdown`（`:166`）需要外部传入 `marked` 实例，且 `patchStrikethrough`（`:143`）会**原地修改**该实例（带 `WeakSet` 去重，`:141`）。测试时需注意补丁的跨用例累积效应。

3. **`server.js` 在被 `require` 时会立即执行 `main()`**（`LightMDKit/server.js:313`），会真的拉起守护进程并尝试打开浏览器。因此**当前无法直接 `require` 它来做接口测试**，需先按 5.4 节的改造建议处理。
